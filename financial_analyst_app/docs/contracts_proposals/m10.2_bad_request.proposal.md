# Contract change proposal: add `bad_request` to the frozen `ErrorCode`

Status: **RAISED 2026-10-02 — awaiting human sign-off. NOT implemented.**
Raised by: M10.2 Slice 2 (`GET /market/candles`), found while implementing the handler.
Format: the `AGENTS.md` §5 change-proposal block, verbatim in shape.

```
Change: Add ErrorCode.bad_request: str  ("bad_request", lower_snake)
Why:   The frozen ErrorCode enum has NO member for "the request itself is malformed".
       Every 422 code is domain-specific (insufficient_margin, exposure_limit, qty_step,
       negative_price, rr_too_low, future_timestamp...). None of them means "you sent a
       bad parameter". The two nearest candidates are both WRONG in a way that causes real
       harm:
         - unknown_state  -> 503 AND listed in envelope._RETRYABLE. Returning it for a bad
           `limit` tells the client to RETRY a permanent caller bug, forever.
         - capability_not_supported -> 422 and correctly non-retryable, but it claims the
           SERVER lacks a capability when in fact the CALLER sent nonsense. A dashboard
           would surface "this broker does not support limit=10000", which is a lie that
           sends an engineer hunting the wrong layer.
Impact:
         - M10.2 /market/candles: bad limit, naive timestamp, inverted range, tampered
           cursor. Currently answered with the stand-in code and a precise `details.reason`.
         - Every future gateway route: same gap. The M10.2 inventory has ~30 proposed
           endpoints and this would be re-decided on every one of them.
         - Frontend: needs to distinguish "your input is wrong" (fix and retry) from
           "the venue is down" (back off and retry) from "no such symbol" (fix the code).
           Today those three collapse into one of two codes.
Bump:   minor (additive enum member + one entry in envelope._STATUS at 422; NOT retryable).
         Existing consumers are unaffected: nothing currently emits it, and no existing
         member is renamed, removed, or re-mapped.
Consumers notified: M10 (all gateway routes), frontend error handling.
Migration: shared/contracts/errors.py (add member) + envelope._STATUS (add 422 mapping)
           + envelope._RETRYABLE (explicitly NOT added) + contract_tests snapshot refresh.
Sign-off: [ ] human LGTM before code
```

## The fix, in full, so review is a diff not a decision

```python
# shared/contracts/errors.py
    bad_request = "bad_request"

# modules/experience/api/v1/envelope.py
    _STATUS: dict[ErrorCode, int] = {
        ...
        ErrorCode.bad_request: 422,     # under the existing "422: the request itself is wrong"
                                       # comment block
    }
    # _RETRYABLE deliberately NOT extended. A malformed request is not worth retrying;
    # `_RETRYABLE`'s own docstring already says "only these are worth retrying".
```

## What I did instead, and why it is not permanent

The handler works today. It returns:

```
422 capability_not_supported
   message: "limit must be between 1 and 500, got 100000"
   details: {"reason": "invalid_limit"}
```

The **status is correct** (422), the code is **non-retryable**, and the precise cause travels
in `details.reason` so the client is never actually misled about what went wrong — only about
which layer owns it.

I did **not** invent `bad_request` in the handler. `AGENTS.md` §10 and proposal §7.2 are
explicit that the gateway "must never invent an error code outside the enum. A new code
requires a contract change with the §5 change process, not an ad-hoc string in a handler."
An ad-hoc string is precisely how a typo like `INSUFFICENT_MARGIN` reaches the wire and the
frontend silently stops matching it — which is the failure `envelope_error` was written to
prevent.

## Recommendation

Approve it. It is additive, it fixes a real misclassification that would otherwise be
re-decided on ~30 future routes, and the alternative is a permanent lie about which layer
owns a caller error. The handler keeps working unchanged after the bump — only the code it
emits changes, which is the point of having the change go through a signature.
