## 0. What this is for, and what it is NOT for

It exists to produce **one honest number**: out-of-sample expectancy after costs, on data
that played no part in choosing the strategy.

It does **not** exist to find a profitable strategy. That distinction is the whole design
constraint, and it is why the acceptance bar in §5 is written the way it is.

**THE HONEST CONSTRAINT ON TODAY'S DATA.** Thirty days of 1-minute bars is roughly 10–40
round-trip opportunities per instrument for a typical swing rule. A walk-forward split into
even 3 folds leaves single-digit trades per test fold. At that sample size a real edge and a
lucky configuration are **statistically indistinguishable**. No amount of harness quality
fixes this — it is arithmetic, not engineering.

So this slice is scoped to deliver a **trustworthy harness plus an honest verdict that may
legitimately be "inconclusive"**. It is not scoped to satisfy G0's exit criterion, which asks
for a *meaningful* out-of-sample number. Meeting that bar is a data question, decided after
the harness exists and can be re-run against more history. Claiming a G0 pass on 30 days
would be the failure mode this whole document exists to prevent.

## 3. Decisions required before implementation

### D1 — How does a continuous strength become a trade? **(highest leverage)**

Every strategy returns a number near zero, not an entry. Something must convert strength
into entry/stop/target/size, and that conversion determines whether the result means
anything. Three candidates:

- **(a) Threshold + ATR stop/target.** Enter when `|strength| ≥ θ`; stop at `k·ATR(14)`,
  target at `m·ATR(14)`. Simple, inspectable, and the standard first cut. `θ`, `k`, `m` are
  themselves parameters, so they must live in the train window like any other.
- **(b) Continuous sizing.** Size ∝ `strength`. No threshold to tune, but position size now
  varies trade to trade, which makes per-trade R multiples ill-defined and the expectancy
  much harder to reason about.
- **(c) Signal only, sizing deferred to M5 Risk.** Purest separation, but M5 is not built,
  so this would make G0 un-runnable now.

**Recommendation: (a).** It keeps one position per signal, so a trade is a clean object with
a hand-checkable PnL, and it defers sizing to M5 exactly as the manual's layering intends.

### D2 — Which ONE strategy and instrument for G0?

G0 says one validated strategy. Candidates: `trend_following`, `mean_reversion`,
`donchian_breakout`, `pullback`, `rsi_overbought_oversold`, `regime_based`.

**Recommendation: `trend_following` on `CRYPTO.BTCUSD`.** BTC is 24/7, so it has no session
gaps, no weekly close, and no holiday calendar — it removes three whole classes of bug from
the first end-to-end run. A forex pair is the *second* test, not the first, precisely because
its calendar is where a harness quietly lies.

### D3 — Parameter search budget

Manual caps search at 50 combinations. Confirm this applies per fold (not per run), and that
the cap is enforced in code rather than by discipline.

**Recommendation: cap per fold, enforced by an explicit counter that raises on overflow.**

## 4. Slice decomposition (one sub-module per §2, strictly serial)

| # | Slice | Delivers | Risk |
|---|---|---|---|
| **1** | `data_engine` + `data_suitability` | PIT-correct, time-ordered replay from Timescale; **blocks `gapped` quality** | low |
| **2** | `virtual_broker` + `fill_model` + `slippage_model` | market fills at `mid ± spread/2`, costs from `profiles.yaml` | **high** — this is where backtests lie |
| **3** | trade simulation | D1 mapping; ATR stop/target; one position at a time | **high** — the D1 decision lands here |
| **4** | `leakage_detector` | **must raise** if any read touches `interval_start > as_of` | **high** — must fail closed |
| **5** | `walk_forward` | folds, frozen params, stitched OOS track | medium |
| **6** | `performance_calculator` | expectancy-after-costs, trade count, Sharpe, maxDD, hit rate, per-fold | low |
| **7** | `gate0_walkforward.py` | re-runnable, prints the number + every assumption | low |

Ordering rationale: **slice 4 (leakage) is placed before 5 (walk-forward) on purpose.** A
harness that computes a beautiful expectancy from data it should not have seen is worse than
no harness, because it is trusted. Leakage detection must exist and be proven to fire before
any result is believed.

Slices 2 and 3 carry the money math and therefore need `Decimal` throughout with a single
`ROUND_HALF_UP` quantize helper, plus 2–3 hand-calc tests per `AGENTS.md` §3.1. Positions
are PnL — money. Floats are not acceptable on this path.

## 5. Done means (proposed, needs your agreement)

M8.1 is `complete` when **all** of these hold:

1. Every slice above has spec + tests-before-code + 100% pass, 0 skipped.
2. `leakage_detector` is proven to **fire** — a deliberately planted future-read raises.
   A leakage detector that has never been seen to fail is not a detector.
3. Every cost assumption is **read from `config/execution/profiles.yaml`**, never hardcoded,
   and the report prints the exact profile used per instrument.
4. The report states, in writing: trade count, period, folds, cost assumptions, and
   **whether the result is decision-grade or inconclusive**. A harness that cannot say
   "inconclusive" is not finished, because it will be pressured into saying "promising".
5. At least one trade's PnL is hand-verified to the cent against the stored bars.
6. The result is reproducible: same data + params + seed → same report (`reproducibility`
   hash per manual §17).

**Explicitly not part of done:** finding a profitable strategy. If BTC trend-following is
inconclusive on 30 days, that is a correct result and M8.1 is still `complete`.

## 6. Edges the spec must handle (carried into each slice's tests)

- **Insufficient history** for the requested fold → `InsufficientData`, never a silent short run
- **Zero trades in a fold** → fold reported as 0 trades, never excluded from the count
- **Feature warmup** (EMA200 needs 200 bars before bar 200) → strategy must not be called before
  its features exist; the barrier is real and must be enforced
- **Session gaps** (FX close 20:55, metals two sessions) → no position carried across a closure
  without an explicit gap rule
- **Missing bar mid-session** (the venue's own 21:07Z crypto hole) → `data_suitability` blocks
  it; the trade spanning it is dropped, not bridged
- **Overlapping signals while in position** → ignored, one position at a time (D1a)
- **Parameter grid overflow** → raise, not truncate
- **Adversarial:** `as_of` in the future; a fold whose train window precedes the store's
  first bar; `typical_spread` = 0 and negative; commission > 100%

## 7. Correctness references

- Fill: manual §17 `fill_model` — market fills at `price + spread`, limit fills on cross
- Costs: `config/execution/profiles.yaml` (venue fact, not a routing guess)
- Look-ahead: `AGENTS.md` §3.4 — no signal may use data unavailable at that `exchange_timestamp`
- Chronological splits only, never shuffled; holdout used **exactly once** (`AGENTS.md` §3.4)
- PIT: `AGENTS.md` §6a — the harness reads through `PIT Data Service`, never `lake.list()`
  directly; `scripts/check_pit_guard.py` must stay green

## 8. Open questions for the human

1. **D1** — threshold + ATR stop/target (recommended), or continuous sizing, or signal-only?
2. **D2** — `trend_following` on `CRYPTO.BTCUSD` first (recommended), or a different pairing?
3. **§4 dependency** — freeze/re-LGTM M4.2's 7 strategies before M8 builds on them?
4. **Fold count** on 30 days — 3 folds (train 15d / test 5d) or 4 (train 12d / test 4d)?
   Fewer folds = more trades per fold but a weaker fit. This is the direct trade-off between
   "enough trades to judge" and "enough history to fit", and on 30 days both are thin.
5. Is an **inconclusive** verdict acceptable as this slice's output, or do you want the
   history load raised first so the verdict has a chance of being decision-grade?
