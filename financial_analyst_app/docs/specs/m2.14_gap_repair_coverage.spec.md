## 1. The defect (measured, not asserted)

`scripts/repair_detected_gaps.py:219-222` reads the **audit's** watermark and uses it as its
own lower bound:

```python
since = await conn.fetchval(
    "SELECT verified_through FROM data_audit_watermark "
    "WHERE instrument_id=$1 AND broker=$2", instrument, DERIV)
probes = await find_repairable(conn, instrument, since, args.max_repairs)
```

`verified_through` is advanced by `verify_universe_data.py` to the newest stored bar, even
though that audit **samples only 5 bars per instrument** (`--sample 5` default). The watermark
therefore claims *"everything before here was verified"* while only a sample was checked.

Measured on live data, `CRYPTO.BTCUSD`, `verified_through = 2026-09-30T20:10:00+00:00`:

| Call | Candidates |
|---|---|
| `find_repairable(conn, inst, <watermark>, 50)` | **0** |
| `find_repairable(conn, inst, None, 50)` | **46** |

**Consequence: the safety net is blind to its own history.** A genuine F1 loss (venue has the
minute, we do not) occurring behind the watermark would never be found, probed, or repaired —
and the run would print `nothing to repair` and exit 0, which reads as success.

This is the exact failure the repair tool was written to prevent: `BackfillDriver` walks
FORWARD from `backfill_cursors.reached` and cannot see behind itself either, so
`repair_detected_gaps.py` is the *only* mechanism that can catch a hole behind the frontier.
Disabling it behind a watermark removes the last line of defence.

**Why it has not caused damage yet.** On live data all 46 candidates are class **F2** (absent
at the venue too — verified by direct `ticks_history` probe), so nothing was repairable
regardless. The bug is latent, not yet lossy. It is still a defect: it disables the net
silently and reports success.

## 2. Purpose

Make the repair tool's coverage independent of another tool's trust boundary, and keep it
affordable by baselining venue absences it has already confirmed.

## 3. Design

**D1 — The repair tool owns its own trust boundary.** `find_repairable` no longer accepts the
audit watermark as its lower bound. It scans the full stored range `[min(interval_start),
max(interval_start)]` for the instrument.

**D2 — Known venue absences are baselined and skipped.** A minute already present in
`known_venue_gaps` for that instrument is not re-probed. This is what that table is for; today
nothing on the repair path reads it, so a full-range scan would re-probe every known absence on
every run forever.

**D3 — Newly confirmed venue absences are recorded.** When a probe shows the venue does not
have the minute, write `(instrument_id, broker, interval_start, reason)` to
`known_venue_gaps` so the next run skips it. The table is the memory that makes D1 affordable.

**D4 — The audit watermark keeps its own meaning.** `verified_through` continues to mean
"the incremental audit has walked this far" and is used **only** by `verify_universe_data.py`.
It is never again read as "there are no gaps before here".

**D5 — No invented data.** Unchanged from today: a minute is written only when the venue
returned it and it is calendar-open. Baselines record *absence*, never a value.

## 4. Correctness

Full-range enumeration is exact, not sampled: for each calendar-open interval returned by
`cal.open_intervals(instrument, lo, hi, "deriv")`, every minute in `[a, b)` is tested for
membership in the stored set. A minute absent from storage and absent from `known_venue_gaps`
is a candidate. This is the existing `find_repairable` loop, unchanged, with `since=None`.

**Cost is measured, not estimated.** Full-range scan of `CRYPTO.BTCUSD` (43,749 stored minutes)
took **0.49 s**. Across 25 instruments that is roughly **12 s** of pure local enumeration, before
any venue call. Venue calls remain proportional to *unbaselined candidates only*, which is the
number that matters.

## 5. Edges (each becomes one test)

- **`since` removed / full range** → candidates from the whole stored span, newest first.
- **Minute already in `known_venue_gaps`** → NOT a candidate; no venue call for it.
- **Probe shows venue lacks the minute** → written to `known_venue_gaps`; `fillable` not
  incremented; `filled` not incremented.
- **Probe shows venue HAS the minute** → written to `candles_1m` with `reference_snapshot_id`;
  `filled` and `confirmed` both incremented; `late_frame_count` untouched.
- **Minute outside any calendar-open interval** → not a candidate regardless of storage state.
- **Empty stored range for an instrument** (zero rows) → returns `[]`, never raises.
- **Single stored bar** → `lo == hi`, no candidates, no crash.
- **`known_venue_gaps` absent** (migration not applied) → treated as empty, full scan proceeds.
- **Idempotence** → a second run over unchanged data reports `found=0` because D3 baselined
  every confirmed absence. This is the observable proof that D3 works.
- **Adversarial:** a `known_venue_gaps` row for a minute we DO have → must not suppress
  anything, must not delete or rewrite the stored bar; it is a record of venue state, not a
  delete instruction.
- **Adversarial:** `verified_through` in the future (clock skew, bad migration) → must have no
  effect whatsoever on this tool. Assert that a future watermark still yields the full 46-style
  candidate set.
