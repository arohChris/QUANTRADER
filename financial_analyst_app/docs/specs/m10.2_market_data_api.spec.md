Status: **DRAFT — human LGTM recorded 2026-10-02. Implementation to follow in serial slices.**
Written: 2026-10-02 after research into how Binance, Bybit, Bitget, WEEX, Bitunix, Bitfinex,

Consumers (planned, in order): `frontend/services/market_data_api.ts`, `frontend/app/MarketPanel.tsx`,

## 0. The three research findings that changed this design

### F1 — Every major venue pushes OHLC bars natively. **Deriv cannot.**

Binance `<symbol>@kline_<interval>` (1000 ms), Bybit `kline.{interval}.{symbol}`, Bitget
`candle1m`, WEEX `BTCUSDT@kline_1m_LAST_PRICE`, Bitunix `market_kline_1min` all stream
**pre-aggregated bars at the client's requested interval**, and each frame carries a closure
flag — Binance `"x": false // Is this kline closed?`, Bybit `"confirm": false // Whether the
tick is ended or not`.

**Deriv's published WebSocket surface contains no candle channel at all** — only `ticks` and
`ticks_history`. Verified against the complete endpoint list at `developers.deriv.com/llms.txt`.

**Consequence: the venue is not our aggregator, we are.** This is not a limitation to work
around; it changes who owns three responsibilities:

| Responsibility | Binance/Bybit | **Us on Deriv** |
|---|---|---|
| Aggregate ticks → interval bars | venue | **we must** |
| Decide bar closure | venue (`x`/`confirm`) | **we must** (our own finality machine) |
| Serve the forming bar | venue | **we must** |

The code for this already exists and is **dormant**: `modules/m2_market_data/broker_candles.py`
(`BrokerCandleIngestor`, FORMING / CANONICAL / FINAL) and `ingestion.py` (`IngestionManager`).
This slice promotes them from unused to load-bearing. Until now they were optional; they are
not optional on this venue.

### F2 — Subscribe returns a **snapshot**, then deltas. That kills the overlap bug.

Bitget: *"The channel will push a snapshot after successful subscription, later on the updates
will be pushed."* Bitunix: *"The channel will push a snapshot after successful subscription."*
Bybit labels the first frame `"type": "snapshot"`.

The classic REST+WS seam — *"the final bar from a REST query often corresponds to the currently
unclosed minute"* — is resolved by the snapshot being **authoritative**. The client never merges
or averages; it replaces the current bar from the snapshot, then applies deltas to that bar.

### F3 — Closure is a **response-level flag**, not a per-bar field.

StratAlerts states it best: `partial_bar_included` — *"true when the final bar in the array is
still forming… the last bar's high, low, close and volume will change as the period progresses.
Do not treat a partial bar as a confirmed candle for setup or signal calculations."*

One field, at the top of the response. Not per-bar, not a separate endpoint. This answers the
open question from the M10.2 draft.

## 1. Scope of this slice

Two read endpoints. Nothing else.

```text
GET /api/v1/market/instruments
GET /api/v1/market/candles?instrument=&interval=&start=&end=&limit=&cursor=
```

Out of scope: analytics, news, signals, trading, WebSocket tick streaming. Per `AGENTS.md` §2,
those are separate sub-modules and none of them may be started early.

## 2. Purpose

Serve venue-authoritative OHLC at any supported interval, over a contract that is
broker-agnostic, PIT-correct, paginated, and honest about how fresh and how complete it is.

## 3. Inputs / outputs

**`GET /market/candles` request**

| Param | Type | Default | Notes |
|---|---|---|---|
| `instrument` | string | required | canonical id, e.g. `CRYPTO.BTCUSD` |
| `interval` | string | required | enum from `shared/timeframes.py`: `1m 5m 15m 30m 40m 1h 2h 4h 24h` |
| `start` | ISO-8601 | `end - default_span` | **rounded down** to the interval boundary |
| `end` | ISO-8601 | `as_of` | rounded down to the interval boundary |
| `limit` | int | 50 | **Inherited from the frozen envelope**, not chosen here: `envelope.DEFAULT_LIMIT=50`, `MAX_LIMIT=500`, via `validate_limit`. A larger request is rejected, never clamped |

Ordering is **oldest → newest** (explicit, so a cursor can never skip or repeat).

### 3a. Amendment — `staleness`/`data_state`/`watermark` live in `data`, NOT `meta`

The draft put these three in `meta`. On reading the frozen envelope that is wrong twice over:

1. `envelope_success(data, *, correlation_id, as_of, schema_version)` builds `meta` itself with a
   fixed shape. Adding fields means **editing a frozen contract**, which under `AGENTS.md` §5 needs a
   Change/Why/Impact/Bump proposal and sign-off.
2. More importantly, it is the wrong home. `meta` is the **transport envelope** and is shared by every
   domain. `correlation_id` and `as_of` describe the *response*. But `data_state` and `staleness_sec`
   describe *this payload* and are domain-specific — an account endpoint has no `data_state`, and a
   market endpoint has no pagination watermark. Putting them in `meta` would make every future domain
   carry market fields it cannot answer.

So they go in `data`, beside `partial_bar_included`. **No contract change, no §5 proposal needed**, and
the envelope stays a stable transport concern. Recorded here rather than done silently.

`data` therefore carries: `instrument`, `interval`, `bars`, `partial_bar_included`, `data_state`,
`staleness_sec`, `watermark`, `expected_bars`, `gapped_bars`.

### 3b. Amendment — limits are inherited, not re-declared

The draft proposed `limit` default 500 / max 2000. `envelope.py` freezes 50 / 500. **The frozen value
wins**: a chart needs ~300 bars to fill a viewport and 500 covers it, so there is no reason to widen a
shared contract for one endpoint. Reusing `validate_limit` also means the reject-not-clamp behaviour is
inherited rather than reimplemented.

**Response envelope** (extends the frozen §7.2 shape)

```json
{
  "data": {
    "instrument": "CRYPTO.BTCUSD",
    "interval": "5m",
    "bars": [
      { "t": "2026-10-02T01:10:00Z", "o": "84809.77", "h": "84820.10",
        "l": "84795.30", "c": "84812.44", "quality": "complete" }
    ],
    "partial_bar_included": true
  },
  "meta": {
    "correlation_id": "uuid",
    "as_of": "2026-10-02T02:15:31Z",
    "staleness_sec": 214,
    "schema_version": "1.0",
    "next_cursor": null,
    "has_more": false,
    "data_state": "DELAYED",
    "reference_snapshot_id": "REF-2026-09-25-001"
  },
  "error": null
}
```

Prices are **strings**, not JSON numbers. `Decimal` all the way to the wire (AGENTS §3.1) — a
float64 cannot represent a 5dp FX price exactly, and a chart that re-parses one will drift.

## 4. Design decisions

**D1 — `interval` is a query parameter, not nine endpoints.** Every researched venue does this
(Binance `interval`, Bybit interval enum, IBKR `bar`). One route serves all nine.

**D2 — The backend owns aggregation; the frontend never re-derives a bar.** Only 1m is stored.
`shared/timeframes.py` is the single vocabulary source (`INTERVAL_MINUTES`), already
drift-locked to M2.4 by a parity test.

**D3 — Aggregation is a TimescaleDB continuous aggregate, not Python.**
`CREATE MATERIALIZED VIEW ... WITH (timescaledb.continuous)` with
`time_bucket(INTERVAL, interval_start)` and `GROUP BY bucket`, plus
`add_continuous_aggregate_policy(..., end_offset => <interval>)`. This is the documented
TimescaleDB pattern for exactly this, and it avoids scanning raw rows per request.

**D4 — `timescaledb.materialized_only = false` (real-time aggregates).** Without it the newest
bucket is invisible until the policy runs, so a 1m chart would lag by a full interval. Documented
behaviour: *"when you create a continuous aggregate, queries to that view include the results
from the most recent raw data."* This is what makes the current bar appear at all.

**D5 — OHLC must use ordered aggregates, never `min(open)`-style shortcuts.**
`first(open)`, `max(high)`, `min(low)`, `last(close)` per bucket. TimescaleDB also ships a native
`Candlestick` composite type, which is the preferred form. `min()`/`max()` on the wrong column is
a silent-wrong-price bug.

**D6 — Reads go through `PITCandleProvider`, never the store directly.** `AGENTS.md` §6a.
`scripts/check_pit_guard.py` stays green. `PITCandleProvider.get_candles()` already exists
(M3.1 Provider Port, A69) and returns 1m `Candle` objects; aggregation is layered above it.

**D7 — `data_state` is an enum, not just `staleness_sec`.** Proposed `LIVE | DELAYED | STALE`.
A number can be rendered by a component that forgets to compare it; an enum forces a switch.
Thresholds: `LIVE ≤ 90 s`, `DELAYED ≤ 15 min`, `STALE` beyond — **subject to human confirmation**.

**D8 — `partial_bar_included` is response-level** (F3). When true, the last bar's OHLC will
change and must not be used for signals.

**D9 — A bucket containing a missing minute is returned with `quality: "gapped"`, never
silently averaged.** We have real venue gaps (metals 2026-09-07, crypto 21:07Z) and they must
survive aggregation as a visible downgrade, not disappear into a clean-looking bar.

**D10 — Rate-limit headers on every response** (`X-RateLimit-Limit`, `-Remaining`, `-Reset`),
Alpaca's pattern, so a client sees its budget before exhausting it rather than after a 429.

## 5. Edges (each becomes one test)

- **Unknown interval** (e.g. `7m`) → rejected, `unknown_timeframe`, not silently snapped
- **Unknown instrument** → `unknown_symbol`
- **`start` > `end`** → rejected
- **`start`/`end` not on an interval boundary** → rounded **down**, documented in the response
- **`limit` 0, negative, or > 2000** → rejected, never clamped
- **Window containing no data** (weekend for FX, a holiday) → `bars: []`, `has_more: false`,
  **HTTP 200 — never a 404**
- **Window entirely before the data frontier** → empty list, with `as_of` and `data_state: STALE`
- **Bucket straddling a session closure** (metals two-session model) → each session aggregated
  independently; **no bar may span a closure**
- **Bucket containing a missing minute** → `quality: "gapped"`, still returned (D9)
- **Zero bars but a valid instrument** → 200 with empty `bars`, never an error
- **`cursor` from a different `interval`** → rejected, never silently resumed
- **Opaque cursor round-trip** → page 2 continues exactly where page 1 stopped, no gap, no repeat
- **Concurrent aggregation policy run during a request** → no torn read; the aggregate is
  transactionally swapped
- **Adversarial:** `interval=1m`, `start` 400 days back → rejected at the range cap, not a scan
- **Adversarial:** prices that lose precision as JSON floats (`1.084205`) → served as strings
- **Adversarial:** `cursor` tampered with → rejected as `bad_request`, not a 500

## 6. Correctness references

- Bar timestamp = **interval open, UTC** — universal across every researched venue
- Closure flag semantics — StratAlerts `partial_bar_included`
- Subscribe-snapshot-then-delta — Bitget, Bitunix, Bybit
- Interval switch = unsubscribe then subscribe — Bitunix, documented explicitly
- Cursor pagination, opaque, stable order — Alpaca `next_page_token`, Matchbook `before`/`after`
- Range cap per interval — Dome (`1m`→1 week, `1h`→1 month, `1d`→1 year)
- Continuous aggregate + real-time setting — TimescaleDB docs
- **Known venue boundary quirk:** Bitget documents that `endTime` past a boundary "may include one
  additional interval… the returned data may start one interval earlier." We already have the scar
  tissue for this — audit class **C1** compared every bar against its predecessor and reported
  25/25 FAIL. Any boundary math here must be pinned by a test with a hand-computed expectation.

## 8. Out of scope — stated so it is not silently dropped

- **WebSocket tick/bar streaming.** F1 means we own the aggregator, which makes it a larger slice.
- **The un-deferred forming candle (A49-a).** `partial_bar_included` is honest about the forming
  bar's *existence*; populating it live needs `IngestionManager` wired as a daemon.
- **Volume.** `tick_count` is hardcoded 1 by the fetcher, so venue volume is unavailable on
  backfilled history. Volume fields are omitted rather than fabricated.
- **Trading surfaces.** Blocked on M5/M6/M7, none started.

## 9. Open questions for the human

1. **`data_state` thresholds** — is `LIVE ≤ 90 s / DELAYED ≤ 15 min` right? With 1m bars, anything
   past ~2 min means the feed has stopped, not that the market is quiet.
2. **Ordering** — oldest → newest (chart-friendly, cursor-stable). Some venues return newest
   first. Confirm.
3. **Default span per interval** — Dome caps `1m` to 1 week. Should we mirror a range cap, or let
   `limit` govern alone?
4. **`GET /market/instruments`** — include only display metadata, or also `execution_profiles`
   (spread/commission) so the UI can show costs? The latter is a small contract addition now and
   an awkward one later.
5. **Ordering of work** — spec → aggregation slice → endpoints → frontend service layer →
   `MarketPanel` swap. Confirm this sequence, or should the frontend wiring go first so there is
   something visible sooner?
