## HUMAN LAW (verbatim — embedded, binding)

> **Calculation Timeframe Law.** Every analytic calculation MUST have an explicit
> resolved timeframe. Request-supplied timeframe is authoritative. If omitted, resolve
> from explicit upstream config/requirement (Bot config → Strategy requirement →
> Analysis request). If unresolvable → REJECT. The resolved timeframe is passed
> unchanged to the `CandleProvider` and determines the candle series. **No hidden `1m`
> default.** (Precedent: Pine v5 made `request.security` timeframe a required explicit
> argument and removed v4's hidden chart-TF default — research report 2026-09-25.)

> **Historical Depth Law.** Depth is declared in bars (`minimum_history + warmup`) or
> as a calendar duration (`"3d"`, `"30d"`). Duration converts via
> `required_bars = ceil(history_duration / timeframe_duration)` (3d ÷ 5m = 864,
> 30d ÷ 1h = 720). Sessions/gaps are the provider's answer (what bars actually exist);
> §8b gates decide readiness — never fabricate bars.

> **Analytic Timeframe Isolation.** M3.2 `compute(candles, params)` has no provider,
> no clock, no I/O — it cannot pull `1m` candles for a `15m` request. The engine
> asserts every fetched `candle.interval == resolved_timeframe` (wrong-series guard).
> An analytic never selects its own timeframe.

> **PIT-vs-Depth Law (ACTION 36).** `as_of` is the **temporal boundary** — *when am I
> evaluating the market?* Historical depth is the **analytical requirement** — *how far
> back must the calculation reach?* They are never one variable and never inferred from
> each other. Callers never calculate dates: `FeatureRequest` carries `as_of` + declared
> requirements; only the Requirement Planner derives `window_start`/`window_end`.

> **Demand-Driven Depth Law (ACTION 36) — two deliberately separate paths.**
> **The database (Timescale/WARM) is the historical truth**; Valkey is hot/current state
> only — never a historical source, never preloaded with every timeframe/depth, never a
> bound on any window (cache = acceleration only).
> **UI path (data-display):** a separate request type (`HistoryRequest`, canon §Two
> request types) with **progressive, optional depth** — "last 200 → another 500 → another
> 2,000" — **no hardcoded maximum**; bounded only by what exists in the DB; short reads
> return available candles + explicit `history_exhausted` marker (boundary, not error).
> **Strategy path (PIT):** exact requirement via the planner — the strategy never asks
> for "whatever is available/cached"; when `available < required` → `INSUFFICIENT`
> (§8b omit + warn) — **never a silent partial calculation**, never a silently shrunken
> window.

> **Planner Dependency Law (ACTION 36).** Required depth resolves over the **dependency
> graph**, not the top-level request alone: requested analytics → transitive registered
> dependencies → requirements union → one chronological window per timeframe. Day-1
> computes `max(minimum_history + warmup, ceil(history_duration/tf))` over that union —
> a dependency needing more bars than its dependent (MACD → EMA12/EMA26 → EMA9 chains)
> **widens the window**. `max(top-level only)` without the union is non-conforming.

| | `FeatureRequest` (this slice) | `HistoryRequest` (canon; impl deferred) |

| Purpose | PIT analytical computation | UI data-display / exploration |

**Multi-timeframe plans:** one `FeatureRequest` = exactly one resolved timeframe

layer that issues that batch is M4/M8 (Out). The strategy always receives **analytic
outputs, never raw database rows.**

## Timeframe resolution (Option A — exact flow)

1. `request.timeframe is not None` → validate against `shared/timeframes.py`
   registry → use **unchanged** as `resolved_tf`.
2. `request.timeframe is None`:
   - resolver injected → `candidate = resolver.resolve(request)`; if `candidate is None`
     → `ValidationError` (unresolvable → REJECT); else validate against registry
     (unknown, e.g. `"7m"` → `ValidationError`) → use unchanged as `resolved_tf`.
   - no resolver injected (Day-1) → `ValidationError`.
3. `resolved_tf` is passed **unchanged** to `provider.get_candles(...)` and stamped
   into the cache key. Nothing downstream may substitute a timeframe.

`TimeframeResolver` (in-module Protocol): `def resolve(self, request: FeatureRequest)
-> str | None` — pure; no I/O. Chain implementation (Bot config → Strategy
requirement → Analysis request) lands with M4; Day-1 tests inject fakes.

## Outputs — frozen `AnalyticsResult` (existing contract, no bump)

- `features: dict[str, float]` — ONLY requested-and-available analytics; values
  exactly as `compute` returned (engine does not round)
- `symbol` — **pinned: `= instrument_id`** (e.g. `"FX.EURUSD"`; not display symbol)
- `capability_status` — `PROXY_LIMITED` if any included feature is proxy, else
  `FULLY_SUPPORTED`; `UNAVAILABLE` when **zero** requested features survived the gate
- `capability_warning` — `"; "`-joined: proxy warnings (`tick_count ≠ volume`),
  **§8b vocabulary**: `WARMUP_INCOMPLETE:<feature>`, `INSUFFICIENT:<feature>`,
  `invalid:<feature>` (nan/inf), `unknown_feature <name>`,
  `<feature> UNAVAILABLE (<reason>)`
- `regime` — set when the requested set includes an analytic declaring
  `provides_regime=True` (Day-1: fixture only), else `None`
- `source_watermark` — provider's max candle `interval_start` epoch-ms (lineage), or
  `None` if no candles

## Flow (exact order)

1. Resolve timeframe per the flow above (law first), then validate the request
   (Pydantic; registry membership; `as_of` tz-aware UTC; features non-empty) →
   `ValidationError` at the boundary.
2. Capability gate per feature (M3.0 `is_available`; `allow_proxy=True` so proxy
   features are **included** with warning — the **strategy** decides acceptability per
   M3.0 Day-1 law). Unavailable/unknown → dropped, reason collected.
3. If nothing survives → return `AnalyticsResult(features={}, capability_status=UNAVAILABLE,
   ...)` with reasons in warning. **Never raise for capability misses.**
4. Load profile: `profiles.get(asset_class)` → merge precedence
   overrides > profile > `REQUIREMENTS.defaults`. Absent section → defaults only.
5. **Requirement Planner** (PIT-vs-Depth + Planner Dependency Laws — callers never
   compute dates): resolve the dependency graph over surviving analytics ∪ their
   transitive registered dependencies, then over that union compute
   `needed_bars = max( minimum_history + warmup,
                       ceil(history_duration / tf_duration) if history_duration )`
   (Historical Depth Law). Derive `window_end = as_of`;
   `window_start = as_of - needed_bars * tf_duration`. Valkey contents **never**
   bound the window (Demand-Driven Depth Law — DB is the historical truth).
6. Provider fetch: `await provider.get_candles(instrument_id, timeframe=resolved_tf,
   window_start, window_end, as_of, broker=request.broker)` (**§6a.4 signature
   verbatim**). **Guards:** wrong-series (`interval != resolved_tf`) and completion
   (`interval_end > window_end` — uncompleted candle leaked in) →
   `FeatureEngineDataError`. PIT availability (`availability_time ≤ as_of`) +
   freshness (empty → caller STALE) are the future provider implementation's §6a.4
   WHERE contract. **Provider exception → typed `FeatureEngineDataError` propagates
   (no silent empty).**
7. Dependency resolution: topological order over `REQUIREMENTS.dependencies`
   (deps auto-computed, values returned only if requested). Cycle → `ValueError` at
   register time, never at request time.
8. Quality gates per analytic (§8b): `len(candles) < minimum_history` → omit +
   `INSUFFICIENT:<f>`; `< minimum_history + warmup` → compute +
   `WARMUP_INCOMPLETE:<f>`; else compute. `compute` runs sync pure (no I/O, no clock).
9. Cache: **read first** (after validation/profile; key = resolved request + effective
   params hash); hit → rebuild `AnalyticsResult` from JSON, measure elapsed; miss →
   steps 5–8 → `setex TTL 60` best-effort. Cache errors swallowed (log) —
   **fail-open to recompute.**
10. Stamp capability fields + `symbol=instrument_id` + `source_watermark`; return
    frozen result.

**Incremental note (architecture §5, Day-1 honest):** stateless full-compute per
request is acceptable while windows are small (Tier-1 warmups ≤ ~60 bars);
incremental-state binds **before** live volume: **TODO(correctness): incremental state
+ event-driven recalc (arch §5/§12) lands with the live event layer, same slice as
AnalysisSnapshot.**

## Edges

- `timeframe=None` + no resolver (Day-1) → `ValidationError` (law: REJECT, no default).
- Resolver returns `None` → `ValidationError` (unresolvable → REJECT).
- Resolver returns unknown value (`"7m"`) → `ValidationError`.
- Provided timeframe unknown (`"7m"`, `"1m; rm -rf"`) → `ValidationError`.
- Resolver-supplied valid TF used **unchanged** (provider called with `"5m"`, cache
  key contains `:5m:`).
- Depth: `history_duration="3d"` @ `5m` → window covers **864** bars
  (ceil(4320/5)); `"30d"` @ `1h` → 720.
- Provider returns candles of wrong interval (`1m` when `5m` resolved) →
  `FeatureEngineDataError` (guard), never merged/converted silently.
- `features=()` → `ValidationError`.
- Naive `as_of` → `ValidationError`.
- Unknown analytic name → dropped via capability gate (`unknown_feature …`), others
  still computed.
- All features unavailable → empty result, status `UNAVAILABLE`, **no exception**.
- Provider returns 0 candles → all analytics `INSUFFICIENT:` → empty features,
  status still `FULLY_SUPPORTED` (gate passed; data thin) with warnings.
- Two different `as_of` → two cache keys; same request twice within 60s → hit (P16).
- `user_id` never appears in key or result (tenant law — request has none).
- Profile missing for asset_class → `ValidationError` at config load (fail-loud
  startup), not per request.
- `param_overrides` beat profile; profile beats defaults (single precedence rule).
- Analytic registered twice → `ValueError` at register; dependency cycle A→B→A →
  `ValueError` at register.
- Calendar timeframe (`"1w"`, `"1mo"`, `"1y"`) → `ValidationError` — registry holds
  only the 9 fixed-duration strings; calendar periods need explicit calendar-bucket
  semantics before being enabled (**never silently treated as fixed-duration**).
- Provider returns a candle with `interval_end > window_end` →
  `FeatureEngineDataError` (completion guard — uncompleted/forming leak).
- Dependency declares larger depth than its dependent (dep min 50, dependent min 5)
  → window widens to the **union** (Planner Dependency Law), never top-level only.
- Identical request at two `as_of` values → identical depth **span**, window shifted
  (PIT-vs-Depth: `as_of` ≠ depth, never one variable).
- `0 < len(candles) < minimum_history` → `INSUFFICIENT:<f>` + `compute` **never
  called** (Demand-Driven Depth Law — no silent partial calculation).

## Adversarial (must be in tests)

- Hostile feature name `"'; DROP TABLE features;--"` → dropped as unknown, no I/O,
  no SQL (there is none) — result still returned for other features.
- Provider raises on purpose → `FeatureEngineDataError` with cause, never empty-success.
- Cache server dead (bad port) → request succeeds via recompute; second identical
  request also succeeds (fail-open proven).
- `compute` returns `nan`/`inf` → omit feature + `invalid:<f>` warning (JSON cannot
  carry NaN — never cache it).
- `timeframe="1m; rm -rf"` → `ValidationError`.

**Terminology — three distinct notions, never conflated:**
1. **Mathematical minimum input** — fewest bars on which the formula is defined

2. **Library first-output lookback** — a specific library's `*_Lookback()` indexing
   (library-specific; verify before importing a number).
3. **Platform warmup / pristine (§8b)** — our execution-quality gate:
   `minimum_history` (INSUFFICIENT) + `warmup` (WARMUP_INCOMPLETE) → pristine at
   `minimum_history + warmup`.
