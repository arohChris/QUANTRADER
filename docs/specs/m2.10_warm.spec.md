## Purpose

Durable **canonical persisted finalized-1m candle store** in TimescaleDB (asyncpg),
plus the **D2 FIFO flush** that moves minutes out of the 4-hour M2.9 HOT ring, plus
**warmup range reads** for the Analysis layer.

Canonical-source law (A33 r2): *M2.4 produces canonical market-state events; the
durable finalized 1-minute candle store (WARM/Timescale) is the canonical persisted
historical dataset.* M2.9 never stores finalized candles (m2.9 spec §forming-key
ownership). M2.8 parquet remains the PIT/backtest lake (§6a `availability_time ≤ T`
unchanged — `check_pit_guard` still governs alpha; Timescale is warm-serving, **not**
the PIT authority).

## Binding decisions (human, 2026-09-25 — recorded in USER_ACTIONS)

- **D1 (LGTM'd "standard"): fold from 1m ONLY.** One 1m ring; all higher timeframes
  derived via a hard-coded-but-extensible **supported-TF registry** shared by UI
  chart / analysis / trading — single definition, zero conflicts; bars reach
  analytics in time for point-in-time analysis. WARM stores **1m only** (base data);
  higher-TF history is folded from stored 1m on demand (fold cache = later,
  optimization only).
- **D2 (confirmed "Keep 4h as decided"): ring = 240 × 1m bars (4h comfort buffer).**
  On each completed 4h window the oldest minutes flush to Timescale **FIFO-style**
  (ascending `interval_start`). Measured 24h option declined.
- **Bound consequence (recorded):** EMA200@1m pristine warmup (250 bars = 4h10m) and
  folds deeper than 4h warm up from Timescale; live-keep on ring. Hybrid read is
  therefore **required** for complete windows: ring = trailing ≤4h, Timescale =
  everything older. Union = complete; the two stores must never both lack the same bar.
- **A42 storage law (human, same day): Timescale = store of record ≥1yr, compression ON.**
  (a) Compression: DDL enables `timescaledb.compress` (segmentby `provider, instrument_id`;
      orderby `interval_start DESC`) + `add_compression_policy('candles_1m', INTERVAL '7 days',
      if_not_exists=>TRUE)` — idempotent, applied by verify/setup.
  (b) Retention ≥365d: v1 has **NO auto-prune** (Out of scope) ⇒ A42-compliant; bible
      `storage.yaml` WARM=90d policy CONFLICTS → flagged in BUILD_STATUS Discrepancies
      (human A42 wins; bible patch needs sign-off).
  (c) Conversion: existing M2.8-lake live-capture rows imported once into Timescale
      table `ticks_live` by the verify script (LakeReader → idempotent upsert);
      raw JSONL stays the source artifact.

## Responsibility boundary (human review amendment A46, 2026-09-25)

> **WARM does not decide strategy history depth or point-in-time semantics.**
> WARM stores and retrieves finalized 1m candles for an explicitly requested time
> range. The caller/service above WARM is responsible for determining the requested
> historical window and enforcing any point-in-time (`as_of`) availability rules.

- WARM does not know whether the caller is a UI, strategy, backtest, analytics,
  charting, or data-repair process.
- **`read_1m` stays range-based** — `read_1m(provider, instrument_id, window_start,
  window_end)`; **no `as_of` parameter, no depth heuristics** (see layering below).
- **Historical-depth requests are caller-controlled:**
  - A **UI/chart request** may explicitly request additional historical depth (e.g.
    another block when the user scrolls backward) — a second explicit range; WARM
    never auto-expands.
  - A **strategy/analysis request** must operate at a defined `as_of` timestamp and
    may request only the historical window required for its calculation.
  - Additional historical depth must never cause a strategy calculation to cross its
    `as_of` boundary.
  - The existence of newer data in WARM must never make that data visible to a
    point-in-time strategy/backtest evaluation.
- **Layering (PIT stays above WARM):**
  `Strategy → PIT/HistoricalDataService (as_of; availability_time ≤ as_of; bar
  completion ≤ as_of) → WARM read_1m(start, end) → TimescaleDB`.
  WARM v1 has **no `availability_time` column** (§1 column list) and therefore cannot
  prove availability-at-T — **faking PIT inside WARM is forbidden**. Matches M3.1's
  future PIT provider seam (`availability_time ≤ T`; §6a law unchanged; WARM never
  used directly by M4 — `check_pit_guard` still governs).
- **`window_hours=4` / `flush_batch_size=240` are WARM buffering/flush operational
  parameters — NOT a platform history-depth limit.** Long depth comes from durable
  storage via the historical-data service.

### Canon rule (locked by this review)

```text
WARM:                durable finalized-1m storage · explicit range reads ·
                      no automatic historical expansion · no strategy semantics · no UI semantics
Historical/PIT svc:  determines required history · resolves as_of ·

UI/history svc:      may explicitly request additional historical depth ·

Strategy:            ALWAYS evaluated at explicit as_of · receives only PIT-valid data ·

```

## Components (what the implementation contains)

### 1. Schema + DDL (idempotent, never run implicitly on import)
- Table `candles_1m(provider, instrument_id, interval_start, interval_end, open,
  high, low, close, tick_count, average_spread, min_spread, max_spread,
  expected_duration_ms, quality_status, aggregation_version, reference_snapshot_id,
  created_at)`.
- Prices: PostgreSQL `double precision` — `Candle` fields are float64; float8
  roundtrips **exactly** (JSON float → pg float8 → back = identical bits). No
  Decimal conversion in this path (market data, not settlement — money-law N/A).
- **UNIQUE (provider, instrument_id, interval_start)** → writes are
  `INSERT ... ON CONFLICT DO NOTHING` (finalized = immutable; re-flush idempotent;
  never UPDATE an existing row).
- Timescale `create_hypertable(interval_start, chunk_time_interval => 1 day)` +
  index `(provider, instrument_id, interval_start DESC)` for range scans.
- DDL applied by verify/setup with `IF NOT EXISTS` — idempotent, human-visible.
  - **A42 compression DDL:** `ALTER TABLE candles_1m SET (timescaledb.compress, timescaledb.compress_segmentby='provider, instrument_id', timescaledb.compress_orderby='interval_start DESC')` (re-runnable SET) + `SELECT add_compression_policy('candles_1m', INTERVAL '7 days', if_not_exists=>TRUE)`.
  - **A42 conversion table:** `ticks_live(provider, instrument_id, epoch, ...)` with `UNIQUE (provider, instrument_id, epoch)` + `IF NOT EXISTS` — target of the one-time lake import (§7).

### 2. Connection (asyncpg pool)
- Async pool; DSN built from env (`TIMESCALE_DEV_PASSWORD` from repo-root `.env` —
  never in code, logs, exceptions, or reprs; redaction test required).
- Sane bounds at startup (§3.13): pool size, connect timeout, statement timeout.
- Transient errors: exponential backoff + jitter; no retry storms.

### 3. Error policy — durable path is NOT fail-open (contrast with M2.9 HOT)
- Writes retry with backoff; persistent failure surfaces as typed error + CRITICAL
  log + held backlog — **never a silent drop of a finalized candle.**
- **Flush-before-evict invariant:** minutes are evicted from the HOT ring only after
  durable ack. A flush batch being pushed out of the 240-window is held until
  Timescale acks; backlog bounded by ring overflow → beyond bound = CRITICAL
  (recovery path: M2.7 watermark backfill + M2.8 parquet are independent and
  already written by the pipeline — documented, never assumed silently).
- Cursor durability: flush watermark per (provider, instrument) persisted in
  Timescale; restart resumes exactly from cursor (at-least-once flush + idempotent
  upsert = effectively once).

### 4. FIFO flush (D2 mechanics)
- Source: HOT 1m ring (240 slots per provider+instrument).
- Trigger: completed 4h window boundary (M2.4 interval event) → dequeue the minutes
  falling out of the window → upsert ascending `interval_start` (FIFO order) →
  advance cursor after ack.
- Backlog retry: periodic timer retries unflushed batches until ack.
- Out-of-order batch arrives (adversarial): still accepted (upsert by key), cursor
  only advances to the max contiguous flushed `interval_start`.

### 5. Warmup reads (range contract — caller-controlled depth, A46)
- `read_1m(provider, instrument_id, window_start, window_end) -> list[Candle]`
  ascending, indexed range scan. History only — **ring merge for trailing ≤4h is the
  analysis layer's job** (consumer law documented here; no cross-store hidden merge).
- **Range invariant (defensive):** every returned row satisfies
  `window_start <= interval_start <= window_end` — WARM filters anything outside the
  requested window and **NEVER auto-expands it** (UI "load more" = a second explicit
  request above WARM; see Responsibility boundary).
- Contiguity / bar-count gates (`INSUFFICIENT`, `WARMUP_INCOMPLETE` per §8b) stay in
  Analysis/M3 — the store returns rows, never invents readiness.
- PIT: rows become queryable at flush time (≥ `interval_end`); backtest PIT authority
  stays M2.8 parquet/lake §6a. Timescale never used by M4 directly (PIT guard).

### 6. Config
- DSN/env refs, pool bounds, flush batch size, 4h window boundary, backlog bound —
  validated sane ranges at startup; refuse to start on absurd values.

### 7. A42 conversion (one-time, verify-driven)
- Source: existing M2.8 parquet live-capture rows (`data/lake/...` ticks, 51 rows as of 2026-09-25) read via frozen `LakeReader.read_partition`.
- Target: `ticks_live` — upsert `ON CONFLICT (provider, instrument_id, epoch) DO NOTHING` (idempotent: verify re-run imports 0 new rows).
- `created_at` defaults `now()`; original `exchange_timestamp` preserved as `epoch` — lineage (`reference_snapshot_id`) carried through.
- Raw `data/live_capture/**/raw_*.jsonl` remains the human-readable source artifact (never deleted).

## Edges (test plan seeds — written when resumed, Step 3)

- Empty instrument (no rows) → `[]`, not error.
- Single bar / boundary start=end inclusive semantics defined.
- Duplicate re-flush of same batch → 0 new rows (idempotent), cursor unchanged.
- Flush with dead Timescale → typed error, batch retained, ring NOT evicted, CRITICAL.
- Restart mid-flush → resume from persisted cursor; no bar lost, no bar duplicated
  (idempotent upsert).
- Cursor regression attempt (older watermark write) → rejected (monotonic — mirror
  A33 discipline).
- Out-of-order + interleaved batches → final stored set identical; cursor =
  max contiguous.
- Redaction: exception/log from connection failure never contains password.
- float64 exact roundtrip: seed bars with representable values (e.g. 1.08538) →
  read-back `==` bitwise.
- Adversarial: junk input (negative `tick_count`, `interval_start > interval_end`,
  unknown quality_status) → typed rejection, store never corrupts (validation is
  M2.3/M2.4's job upstream — store still refuses to persist garbage).
- Hypertable/DDL applied twice → no error, no duplicate objects.
- Range boundary (A46): `read_1m` window args reach SQL verbatim (`$3/$4`); returns
  only rows with `window_start <= interval_start <= window_end`; no synthetic padding;
  rows outside the window (even if the DB returned them) are filtered, never added to.
