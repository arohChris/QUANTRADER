## 1. Purpose

One function that turns any result into the §4 envelope, and one function that turns any
exception into the envelope's error shape using **only** frozen `ErrorCode` values.

## 2. Scope

**In:** envelope construction · `meta` population · error translation and HTTP status
mapping · `schema_version` policy · pagination metadata and validation.

**Out:** authentication, tenant resolution, routing, any store access, any business value.
Those are leaves 2–9. A handler calls this leaf; this leaf never calls a handler.

## 3. Signatures

```python
def envelope_success(data, *, correlation_id, as_of, schema_version) -> dict
def envelope_error(code, message, *, correlation_id, as_of,
                   retryable=False, details=None) -> dict
def http_status_for(code) -> int
def validate_limit(raw) -> int          # 1..500, raises on violation
def paginate(rows, *, limit, cursor) -> Page
```

`as_of` is a timezone-aware UTC `datetime`. `code` is an `ErrorCode` member — **not** a
string. Accepting a bare string is a defect, because it is the only way an unvalidated code
can reach the wire.

## 4. Invariants

1. `data is None` **iff** `error is not None`. Never both, never neither.
2. `meta.correlation_id` is always present and always echoes the request id.
3. `meta.as_of` is always RFC-3339 with an explicit `Z`, never naive, never local.
4. `error.code` is always a member of the frozen `ErrorCode` enum.
5. `error.code == "detail"` and any FastAPI `detail` string **never** reach the wire.
6. Money values are serialized as JSON **strings** (`"12.00"`), never JSON floats.
7. The builder is **pure** — no I/O, no clock read, no global state. `as_of` is injected.
   Purity is what makes the tests deterministic and replayable.
8. Unknown error codes cannot be constructed: the type rejects a non-enum value.

## 5. Error-code → HTTP status mapping

Derived from `status_code` already declared on the exception hierarchy, **not** invented
per handler. `financial_analyst_app/shared/core/exceptions.py:14-26`

| Class | Status |
|---|---|
| auth missing/invalid | `401` |
| authenticated but not permitted | `403` |
| malformed input, bad limit, bad cursor, naive `as_of` | `422` / `400` as declared by the raising site |
| unknown instrument | `404` |
| `trade_plan_expired`, gate conflict | `409` |
| `insufficient_margin`, `exposure_limit`, `leverage_limit`, `concentration_limit`, `rr_too_low`, `missing_sl_tp`, `qty_step`, `insufficient_qty` | `422` |
| `stale_signal`, `stale_alpha`, `data_quality_invalid`, `gap_detected` | `409` |
| `capability_not_supported`, `unknown_symbol` | `422` / `404` |
| `broker_unavailable`, `unknown_state` | `503` — **and retryable** |
| anything unmapped | `500`, `retryable=false` |

`unknown_state` maps to `503` deliberately: an unresolvable state must never be reported
as a success or a client error. `AGENTS.md` §3.3

## 6. Edge cases

| # | Case | Required behaviour |
|---|---|---|
| E1 | success, empty dict payload | `200`, `data={}`, `error=None` |
| E2 | success, empty **list** payload | `200`, `data=[]`, `error=None` — never `404` |
| E3 | error | `data=None`, `error` populated, status from §5 |
| E4 | `correlation_id` omitted by caller | `TypeError` — it is required, not defaulted |
| E5 | naive `as_of` (no tzinfo) | `ValueError` — UTC is mandatory. `AGENTS.md` §3.8 |
| E6 | non-UTC tzinfo | normalized to UTC, offset applied, never relabelled |
| E7 | `Decimal("12.00")` in data | serialized as `"12.00"`, never `12.0` |
| E8 | `Decimal("0.001")` price | serialized as `"0.001"`, never `1e-3` |
| E9 | `limit=0` | `ValueError` |
| E10 | `limit=501` | `ValueError` — **rejected, not clamped** |
| E11 | `limit=500` | accepted |
| E12 | `limit` non-numeric | `ValueError` |
| E13 | `limit` absent | default `50` |
| E14 | rows exceed `limit` | truncated, `has_more=True`, `next_cursor` non-null |
| E15 | rows exactly `limit` | `has_more=False`, `next_cursor=None` |
| E16 | rows fewer than `limit` | all rows, `has_more=False` |
| E17 | malformed cursor | `ValueError` — never a partial page |
| E18 | unknown error code string | `TypeError` at construction |
| E19 | exception with `details` | `details` preserved verbatim |
| E20 | exception without `details` | `details={}`, never `null` |

## 7. Adversarial — not in §6, must fail safe

| Input | Must |
|---|---|
| `error.code` = `"__class__"` | `TypeError`, no attribute traversal |
| `details` = `{"__proto__": 1}` | preserved as inert data, never merged into a prototype |
| `correlation_id` = 1 MB string | `ValueError` on length, not stored |
| `as_of` = year 9999 | accepted if tz-aware; rejected if naive |
| `Decimal("NaN")` in data | `ValueError` — never emitted as invalid JSON |
| cursor = 1 MB garbage | `ValueError` fast, no unbounded parse |
| `limit` = `-1` | `ValueError` |
| `data` containing a `Decimal` nested 5 levels deep | serialized as a string at every level |

## 8. Definition of correct

- A handler can build any response in one call and never touch the envelope shape.
- A frontend can branch on `error.code` alone and never parse prose.
- The same input always produces byte-identical output (purity, §4.7).
- No float ever appears in a money position of the serialized output.

## 9. Tests required before implementation

In `tests/m10_2/test_m10.2_envelope_spec.py`:

- one test per §6 edge, named after the case;
- the §7 adversarial cases, each asserting a **specific** raised type or value;
- **hand-calc money asserts** — exact string equality on the serialized form, never
  `pytest.approx`:
  ```python
  # Hand calc: Decimal("12.00") must serialize as the string "12.00" (2dp quote ccy,
  # ROUND_HALF_UP at the settle boundary) — never the float 12.0.
  assert body["data"]["pnl_net"] == "12.00"
  ```
- a determinism test: two calls with identical injected inputs are byte-identical;
- a test asserting **no** `detail` key ever appears at any level of the payload.

## 10. Line budget

Target ≤180 lines implementation. Over-budget is a §3.14 deviation and must be flagged
before it is accepted, not after.

## 11. Open questions

1. Should `envelope_error` accept an `ErrorCode` **or** an `Exception`, converting via its
   `error_code` + `status_code`? The second is more ergonomic; the first is stricter.
   **Recommend:** both, with the exception form delegating to the enum form.
2. `next_cursor` encoding — opaque base64 of the sort key, or an opaque store-side token?
   **Recommend:** store-side token, so the frontend cannot infer ordering.
