# Spec: M2.7 Backfill Driver - turn months of broker history into stored bars

Purpose: One re-runnable program that walks **months** of past time for one instrument, asks the calendar which minutes were tradable, fetches only those, writes them to Timescale, survives being interrupted, and **refuses to launder a calendar mistake into permanent data loss**.

This is the **G0 critical path**. G0 exit requires `scripts/gate0_walkforward.py` plus a documented out-of-sample expectancy-after-fees number (`AGENTS.md` §1). A walk-forward cannot run on the 9.03 hours currently stored, so this driver is what turns the built pipeline into usable history.

Review status: **DRAFT 2026-09-29. Awaiting human LGTM (Step 1). No tests, no code written.**

## 1. The one design decision that matters most

**`backfill.py:315-322` marks an empty broker response as `TERMINAL` and writes `GapLedger.record_permanent(PERMANENTLY_MISSING)`.** That is correct *when the caller only asks for windows it believes are tradable and the calendar is right*.

**It is catastrophically wrong for a driver whose windows come from a calendar we know is wrong.** Concrete, already-measured case: our config says forex closes Friday **21:00**; the broker closes **20:55**. A driver trusting `open_intervals` would ask for 20:55-21:00 every Friday, receive nothing, and write a **permanent missing** record — which `_classify:245-248` then honours forever. Result: ~130 permanent holes, one per week, and every real gap in those same windows permanently masked. **A backfill that invents permanence from a config error is worse than no backfill**, because it converts a visible bug into invisible data loss.

### The rule

> **The broker is authoritative about its own data. The calendar is our config. When they disagree, the BROKER wins and the disagreement is reported loudly.**

| Calendar says | Broker returns | Outcome | Never |
|---|---|---|---|
| CLOSED | *(never asked)* | skip | contact the broker for a closure |
| OPEN | bars | `FILL` | |
| OPEN | **empty** | **`CALENDAR_DISCREPANCY`** + `UNRESOLVED` | **`TERMINAL` / `record_permanent`** |
| OPEN | error | `UNRESOLVED` | terminal |
| unknown | *(never asked)* | refuse to run | guess |

So the driver **does not delegate the empty-response branch to the coordinator's terminal path.** It must intercept it. This is a deliberate divergence from `BackfillCoordinator`'s T5 rule, it is recorded here, and it is the single most important behaviour in this slice.

**Consequence, stated honestly:** a genuinely unrecoverable window is now retried on later runs instead of being learned as permanent. That is the correct trade here — a wasted broker call is cheap, a masked real gap is not. The retry cost is bounded by the cursor (§4), so it cannot become a runaway.

## 2. Inputs / Outputs / Invariants

### Inputs
- `instrument_id: str` - canonical, e.g. `CRYPTO.BTCUSD`.
- `broker: str` - `deriv`.
- `start`, `end: datetime` - **tz-aware UTC, half-open `[start, end)`**.
- `--max-span-minutes` - cap per broker request; **default 1000**, from `history.py:60`.
- `--min-interval-ms` - throttle between broker requests; **default 250**, see §6.
- `--resume` / `--fresh` - continue from the stored cursor, or ignore it.

### Outputs
- Bars in `candles_1m` (`quality_status = 'backfill'`), written `ON CONFLICT DO NOTHING`.
- A row per run in a new additive table `backfill_runs` (§4).
- A **human-readable report** to stdout: requests, bars written, windows skipped as closed, discrepancies, unresolved, duration.

### Invariants (each separately testable)
- **I1 NO CLOSURE IS EVER REQUESTED.** A window the calendar calls closed never reaches the broker. Asserted by counting broker calls, not by inspecting logs.
- **I2 NO PERMANENT RECORD FROM A CALENDAR-DERIVED WINDOW.** `GapLedger.record_permanent` is **never called** by this driver. Asserted by a spy ledger.
- **I3 HALF-OPEN THROUGHOUT.** Windows are `[start, end)`. A candle's `interval_start` is the START of its minute. The `+1` convention for closed sets **must not** appear anywhere in this slice - it is correct for Deriv's returned set and wrong for our windows, and applying it manufactures a phantom gap at the end of every window.
- **I4 RESUMABLE.** A run interrupted at request *N* resumes at *N+1* without re-requesting. Asserted by a counting fake across two runs.
- **I5 THE FORMING BAR IS NEVER STORED.** With `end` in the past every returned bar is final; the driver additionally **drops any bar whose `interval_end > run_end`**, because a bar for an in-progress minute is partial and `ON CONFLICT DO NOTHING` means it could never be corrected.
- **I6 EVERY DISCREPANCY IS REPORTED, NEVER ABSORBED.** A calendar/broker conflict appears in the report with its window. Silence is a failure.

## 3. Algorithm

```
1. validate inputs (aware UTC, start < end, end <= now)
2. cursor = load_backfill_cursor(instrument)  if --resume else start
3. windows = calendar.open_intervals(instrument, cursor, end)   # O(days), not O(minutes)
4. for each open interval:
       for each chunk of at most max_span_minutes:
           a. ask the broker once
           b. bars   -> write to candles_1m, record progress
              empty  -> CALENDAR_DISCREPANCY, do NOT mark permanent
              error  -> UNRESOLVED, back off, stop this run cleanly
           c. throttle min_interval_ms between requests
           d. persist cursor after every successful write
5. write backfill_runs row; print report
```

**Why `open_intervals` and not `is_open` per minute** — the primitive already exists at `calendar.py:356` and its own docstring records the failure it was written to fix: *"the first gap-detection build asked 'is this minute open?' once per minute. A ten-year window is ~5.2M calls, which does not finish."* Reusing it also means gap detection and backfill cannot disagree about what was tradable.

**Sequential, not concurrent.** A run is ~130 requests. Concurrency would gain little and would make the throttle, the cursor and the rate-limit handling three more things to get right. Simplicity wins; concurrency is a later, separate slice if measurement demands it.

## 4. Resumability (additive DDL)

```sql
CREATE TABLE IF NOT EXISTS backfill_cursors (
    instrument_id text NOT NULL,
    broker        text NOT NULL,
    reached       timestamptz NOT NULL,
    updated_at    timestamptz NOT NULL DEFAULT now(),
    UNIQUE (instrument_id, broker)
);

CREATE TABLE IF NOT EXISTS backfill_runs (
    run_id            uuid PRIMARY KEY,
    instrument_id     text NOT NULL,
    broker            text NOT NULL,
    requested_start   timestamptz NOT NULL,
    requested_end     timestamptz NOT NULL,
    started_at        timestamptz NOT NULL,
    finished_at       timestamptz,
    requests          integer NOT NULL DEFAULT 0,
    bars_written      integer NOT NULL DEFAULT 0,
    closed_skipped    integer NOT NULL DEFAULT 0,
    discrepancies     integer NOT NULL DEFAULT 0,
    unresolved        integer NOT NULL DEFAULT 0,
    status            text NOT NULL DEFAULT 'running',
    note              text
);
```

Both `CREATE TABLE IF NOT EXISTS` - **additive only, no migration, no existing table touched.** `flush_cursors` is the LIVE ring-flush cursor and is a different thing; it is **not** reused, because its monotonic rule (`warm.py`) belongs to the live path and coupling them would make a backfill advance the live watermark.

`status` is `running | complete | stopped_early | failed`. A row stuck at `running` means the process died; the driver reports it rather than hiding it.

## 5. Edge cases (one test per row)

| ID | Condition | Required behaviour |
|----|-----------|---------------------|
| E1 | window is 0 minutes wide | never reaches the broker |
| E2 | interval longer than `max_span` | split into `ceil(n/max)` chunks, **non-overlapping, lossless** (union == original) |
| E3 | instrument closed for the whole range | `closed_skipped == minutes`, **0 requests** |
| E4 | weekly closure (Sat→Sun FX) | zero requests inside it |
| E5 | a chunk straddles a session boundary | split at the boundary, so no request spans a closure |
| E6 | broker returns bars outside the requested window | clipped to `[start, end)` |
| E7 | broker returns duplicate `interval_start` | deduplicated |
| E8 | broker returns a bar with `interval_end > run_end` (forming) | **dropped**, counted separately (I5) |
| E9 | broker returns unsorted bars | sorted before write |
| E10 | zero-price or inverted bar | dropped as bad data, window stays `UNRESOLVED` - **never** terminal |
| E11 | empty response for a calendar-OPEN window | **`CALENDAR_DISCREPANCY`**, `record_permanent` **not** called (I2) |
| E12 | `429` / rate limit | exponential backoff with jitter, retried, `backoff_seconds` reused from `warm.py` - never a retry storm (§3.8) |
| E13 | socket error mid-run | run ends `stopped_early`; the cursor reflects only **committed** bars |
| E14 | run interrupted then `--resume` | starts at the cursor, re-requests **nothing** already written |
| E15 | `--fresh` | cursor ignored, whole range re-planned; `ON CONFLICT DO NOTHING` makes it safe |
| E16 | start is in the future | `ValueError` before any I/O (`backfill.py:134` precedent) |
| E17 | naive `start`/`end` | `ValueError` - UTC only (§3.8) |
| E18 | `end - start` exceeds the coordinator ceiling | `ValueError`, never a giant single window |
| E19 | cursor is **ahead** of `end` (already complete) | 0 requests, `status=complete`, no error |
| E20 | a previous run row is still `running` | reported, not silently overwritten |
| E21 | zero bars exist in the DB at the start | not an error - the driver is a loader, not a repairer |
| E22 | instrument unknown to the reference master | `ValueError` before any broker call |

## 6. Adversarial (fail-closed, typed error)

| ID | Input | Required behaviour |
|----|-------|---------------------|
| A1 | `max_span_minutes = 0` or negative | `ValueError`; never an infinite chunk loop |
| A2 | `max_span_minutes = 1` | 1-minute chunks, correct count, bounded work per tick (§4.1) |
| A3 | `min_interval_ms` negative | `ValueError` |
| A4 | 10-year range | **refused** unless `--max-span-minutes` and a row budget are both given; a 10-year 1m load is 5.2M rows and must be a deliberate act |
| A5 | calendar raises mid-planning | `status=failed`, **no** write, cursor untouched |
| A6 | write raises mid-batch | `status=failed`; the cursor is advanced only for bars **confirmed written**, so resume re-requests the unconfirmed tail |
| A7 | broker returns a bar for a date the calendar says is a **holiday** | `CALENDAR_DISCREPANCY` reported, bar still written (the broker is authoritative) |
| A8 | `instrument_id` containing quotes/newlines | safe in SQL (parameterised) and in the report |
| A9 | broker returns a candle for the **future** | dropped, counted, never stored |

## 7. Definition of correct

1. **No closure requested** - a spy fetcher proves broker call count equals the number of open-window chunks, and 0 when the range is fully closed.
2. **No permanent laundering** - a spy `GapLedger` proves `record_permanent` is never invoked by this driver.
3. **Lossless chunking** - for random spans and caps, `union(chunks) == original window` and `len(chunks) == ceil(n/cap)`. Property-checked, not example-checked.
4. **Resumable** - two runs with a forced interruption between them issue disjoint broker-call sets, and together cover the range exactly once.
5. **Idempotent** - a third identical run issues **0** requests (everything already written) and writes **0** duplicate rows.

**Second implementation required (§3.1).** The chunking and coverage math must be cross-checked against an independent implementation (e.g. `dateutil`-style interval arithmetic written differently, or a set-of-minutes model for a small window). Interval bugs are exactly the class that a single implementation gets consistently wrong.

## 8. Verification (Step 7, real data)

`scripts/verify_m2.7_backfill_driver.py`:

1. **Live 24h window** for `CRYPTO.BTCUSD` → expect ~1440 requests-worth of bars in ~2 requests, written and **read back from Timescale**, with `bars_written` matching the DB delta.
2. **A known-closed window** (e.g. an FX weekend, or the 20:55-21:00 Friday residue) → **0 requests**, proving I1 against a real calendar disagreement.
3. **Resume proof** - run with `--max-span-minutes` small enough to force several chunks, interrupt, resume, and show the broker-call sets are disjoint.
4. **Idempotency proof** - re-run, show 0 requests and 0 new rows.
5. **Discrepancy proof** - request a window the calendar says is open but the broker denies; show it reported and **not** written to the ledger.
6. **Rate-limit observation** - print actual request pacing; report the observed `429` behaviour honestly (SKIPPED with consequence if it cannot be provoked).

## 9. Explicitly OUT of scope

- **The Friday early-close / `SessionRule` overlay (item #1).** This driver is written to be **safe while the calendar is still wrong** (§1) - that is precisely why the discrepancy branch exists. But it will surface every disagreement loudly, so it is far more useful *after* #1 lands. Dependency is soft, not blocking.
- **The repair loop (item #2).** This driver LOADS history; it does not repair live holes. A future slice may consume the cursor for periodic top-up.
- **M8 / `gate0_walkforward.py`.** Separate slices. This driver is their prerequisite, not a substitute.
- **Any `shared/contracts` change.** No new contract; `BackfillOutcome` is reused.
- **Changing `BackfillCoordinator`'s T5 rule.** The divergence in §1 is enforced in the **driver**, leaving the frozen coordinator untouched. A change there would need its own §5 proposal.
