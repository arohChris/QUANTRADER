# Spec: M1.4 Money Precision (`shared/core/money.py`)

Status: **DRAFT — awaiting human LGTM (Step 1 of AGENTS.md §2). No implementation may start before Step 4 test review.**
Supersedes: nothing. Amends `AGENTS.md` §3.1 scope (settlement money) and the `float` money fields in M1.1 contracts.

## 1. Purpose

One authority for every monetary and numeric quantity in the system, so that no balance, PnL, fee,
price, quantity or margin value can be silently altered by binary floating-point error — and so that
any attempt to do so **fails loudly at the offending line** rather than producing a wrong number.

## 2. Why this is a blocker, with measured evidence

All figures below were measured on this codebase's actual stack
(Python 3.14.6, pydantic 2.13.4, asyncpg 0.31.0, pyarrow 25.0.1, PostgreSQL 17.11, TimescaleDB 2.30.1).

| Test | Result |
|---|---|
| `float("2000000075959.342")` | stored as `2000000075959.342041015625` — **error `+0.000041015625`**, yet *prints* identically |
| Representable gap at 2e12 | `0.000244140625` (via `math.ulp`) — a 3-dp value never lands on the grid |
| 100,000 × `0.0000001` in float | `0.009999999999994874`; `== 0.01` is **False** — silent wrong answer |
| `float round()` on `0.015` | `0.01` (should be `0.02`) |
| `float round()` on `2.675` | `2.67` (should be `2.68`) |
| `Decimal` default context | `prec=28` — a 41-digit value **loses its tail silently** |
| `Decimal.quantize` at `prec=10` on 2e12 | raises `InvalidOperation` — a crash inside a risk path |
| Stray `localcontext(prec=6)` | `2000000075959.342 + 0.01` → `2.00000E+12` — **catastrophically wrong** |

**The failure mode is accumulation, not magnitude.** Every step of a float sum looks correct; the total
is wrong. IEEE-754 addition is also **not associative**, so the same set of fills summed in a different
order can yield a different total. A test suite that only asserts quantized outputs will pass with float
money and still ship an unbalanced ledger.

## 3. Type law

| Domain | Type | Rule |
|---|---|---|
| Settlement money: balance, equity, cash, margin, PnL, fees, commission, ledger postings, `qty`, prices, `stop_loss`, `take_profit`, `exposure` | `Decimal` | Never `float`. Never `int`. |
| Money-participating ratios: `leverage`, `slippage_bps` | `Decimal` | They enter money arithmetic (leverage *divides* margin; slippage *is* a cost). The one float that poisons a `Decimal` expression must not exist. |
| Non-money measurements: `signal_strength`, `latency_ms`, `latency_budget_ms` | `float` | A bounded score or a duration. Never enters money arithmetic. Precision here is not a correctness concern. |
| Exact rationals mid-calc: ratios, hedge ratios, lot fractions, probabilities with no terminating expansion | `fractions.Fraction` | `1/3` is `0.333…` at `prec=28` (truncated) but exact in `Fraction` forever. |
| Market-data candle prices (`candles_1m`) | `double precision` | Retained per `m2.7_backfill.spec.md` §9b. Justified numerically: BTC `84296.692` is 8 significant digits where a double's ULP is ~1.5e-11 — ~7 orders of magnitude of headroom. A 2e12 balance has **none**. |

**Self-enforcement (measured):** `Decimal('0.4') * 0.2` and `Decimal('100.00') + 0.1` both raise
`TypeError: unsupported operand type(s)`. Converting the contracts therefore converts a class of
*silent wrong answers* into *loud failures at the exact line*. This is the single strongest argument for the change.

## 4. The single authority — `shared/core/money.py`

Does not exist today, yet `AGENTS.md` §3.1 cites it. It is created by this slice and is the **only**
permitted route to a money value. It owns and nothing else may duplicate:

1. **Context precision** — set explicitly to `prec=34`, never inherited. Rationale: worst-case domain
   requirement is **16 significant digits** (BTC at max supply, 8dp: `21000000.00000000`), so 34 is
   roughly double the domain. The default 28 is not relied upon, and a hostile foreign `localcontext`
   must not change our results (§2, last row).
2. **`quantize_money(value, scale)`** — the ONLY rounding function, `ROUND_HALF_UP`, applied **once at
   the money boundary**. Per-step rounding is how an institution loses a cent per fill.
3. **`assert_decimal(value)`** — rejects `float` and `int` at the boundary with a typed error.
   `Decimal(0.1)` would inherit `0.10000000000000000555…`, so a float must never reach this module.
4. **Scale registry** — money scale per currency (USD/EUR `2`, JPY `0`, KWD `3`) and price scale per
   instrument. Config-driven in `config/reference/scales.yaml`, never hardcoded, so adding a currency or
   instrument is a config change and not a migration.
5. **Domain bounds** — `max_balance`, `max_notional`, `max_qty`, `max_price`, validated at startup.
   `AGENTS.md` §3.13: the system **refuses to start** on an absurd value rather than run with it. Bounds
   are sized for **the largest accumulator the field will ever hold**, not a single transaction.

## 5. Rounding law

- Compute at full working precision, then **quantize once** when creating the ledger posting. The stored
  amount is the money; an unrounded residual never becomes a stored balance.
- `ROUND_HALF_UP` on both signs: `0.005 → 0.01`, `0.015 → 0.02`, `2.675 → 2.68`, `-0.005 → -0.01`.
- A **formatted display string is never written back** to storage. Format at the edge only.
- A value with **more scale than permitted is rejected, never silently truncated** — silent rounding is
  how money goes missing.

## 6. Boundary law

- Construct `Decimal` **from `str`**, never from `float` (`history.py` already uses
  `json.loads(..., parse_float=Decimal)`; this extends the same discipline to every money boundary).
- `Decimal` does **not** rescue an already-lossy input: `Decimal(0.1+0.2)` = `Decimal('0.30000000000000004')`.
  It stops us *adding* error; it cannot remove error already present. The boundary must therefore be clean,
  which is precisely why the contract field types must change.
- On the wire, money serialises as a **JSON string** (`{"qty":"0.4"}`), never a JSON number — matches
  documented practice that monetary amounts must not become IEEE-754 doubles in a consumer.

## 7. Storage law

- Money columns are `NUMERIC(38,18)` — 38 significant digits, 18 decimal places, sized for the largest
  accumulator. Never `FLOAT`/`REAL`/`DOUBLE PRECISION`. Never PostgreSQL `money` (locale-bound).
- **Verified:** `asyncpg 0.31.0` returns Python `Decimal` for `NUMERIC(38,18)`, exactly, with all 18
  decimals preserved (`2000000075959.342` → `Decimal('2000000075959.342000000000000000')`, `exact=True`).
  The widely-quoted "driver returns float for a DECIMAL column" hazard **does not apply here**. This is
  re-asserted by test, not assumed.
- Parquet uses `decimal128(38,18)`. `pyarrow` rejects an out-of-range value at write time, which is a
  guard rail we want and will test.
- A `SUM()` over a `double precision` column returns `double precision` — the *accumulator* becomes a
  float. So no money aggregate may ever run over a candle column.

## 8. Contract remediation (M1.1) — the field list

`float` → `Decimal`: `Position.qty`, `Position.avg_entry`, `Position.unrealized_pnl`,
`Position.realized_pnl`; `PortfolioState.cash`, `equity`, `margin_used`, `margin_available`,
`exposure`; `OrderIntent.qty`, `limit_price`, `stop_loss`, `take_profit`; `Order.qty`, `price`,
`stop_loss`, `take_profit`; `RiskDecision.approved_qty`; `Fill.price`, `Fill.qty`, `Fill.commission`;
`ExecutionResult.avg_fill_price`; `PortfolioState.leverage`; `ExecutionResult.slippage_bps`.

Stay `float` (documented, not accidental): `Provenance.signal_strength`, `ExecutionResult.latency_ms`,
`RiskDecision.latency_budget_ms`.

Bump: **major `1.0 → 2.0`** — `float → Decimal` is not backward-compatible for equality and changes the
JSON wire format. Requires an `AGENTS.md` §5 change proposal naming every consumer, plus human sign-off,
plus a migration and a snapshot test.

## 9. Edges — expected behaviour

| Edge | Behaviour |
|---|---|
| `float` passed to any money constructor | Typed error `MoneyTypeError`. Never coerced. |
| `int` passed to a money constructor | Typed error — an int is a count, not an amount. |
| Value exceeding declared scale | Rejected. Never silently rounded/truncated. |
| Value exceeding `max_balance` / `max_notional` | Rejected at boundary **and** at startup. |
| Hostile foreign `localcontext(prec=N)` active | Money results **unchanged**; context is managed internally. |
| `Decimal("0")` vs `Decimal("-0")` | Normalise to `Decimal("0")` — no negative zero in a ledger. |
| Quantity `0` | Allowed (position flat). Distinct from "missing", which is `None`. |
| Currency scale absent from registry | Refuse to start (`AGENTS.md` §3.13). |
| Unknown currency code | Typed error. Never assumed to be 2dp. |
| `NaN` / `Infinity` anywhere in money | Typed error — JSON cannot carry them and they are not money. |
| Value with 40+ significant digits | Rejected as beyond the declared domain, not silently rounded. |
| Aggregation over mixed scales (2dp + 8dp) | Rejected — scales must be equal before summing. |

## 10. Adversarial cases (not in the edges above by design)

| Input | Required outcome |
|---|---|
| `"1e400"` | Rejected (out of domain), not `Infinity` |
| `"NaN"`, `"-Infinity"` | Typed error |
| `"  12.50  "` (whitespace) | Accepted, normalised to `12.50` |
| `"1_000.50"` (underscore) | Rejected — not a valid money literal |
| `1e-9` (more scale than 2dp) | Rejected, not truncated to `0.00` |
| Very large `qty` (`1e12`) | Rejected by `max_qty` |
| Currency `"BTC"` with 2dp assumption | Rejected — BTC is not 2dp; must be configured |
| Empty string / `None` | Typed error, distinct messages |
| Byte input `b"12.50"` | Rejected — must be `str`, not bytes |

## 11. Definition of correct

Money correctness is **proven**, not asserted. `shared/core/money.py` is complete only when:

1. `2000000075959.342` and the 8-dp satoshi boundary are **exactly** representable, with no `float` in
   the path (asserted with `Decimal("…")` equality — never `pytest.approx`).
2. 100,000 additions of `Decimal("0.0000001")` total **exactly** `Decimal("0.01")`.
3. The same 1,000 amounts summed in 5 different orders produce a **byte-identical** total
   (order-independence, per non-associativity).
4. Every rounding case in §5 is exact, including negatives.
5. `Decimal ↔ str ↔ JSON-string ↔ NUMERIC(38,18) ↔ parquet decimal128(38,18)` round-trips are all exact.
6. A hostile `localcontext(prec=6)` does not change any result.
7. Every money formula is **diffed against an independent `Fraction`-based implementation**
   (`AGENTS.md` §3.5) and matches to the cent.
8. At least 2 hand-computed asserts with explicit `# Hand calc:` comments and exact
   `Decimal("…")` expectations (`AGENTS.md` §2 Step 3) — e.g.
   `# Hand calc: 0.4 lots * 1.08430 = 0.43372; fee 0.01 -> 0.42372`
   `assert quantize_money(Decimal("0.4") * Decimal("1.08430") - Decimal("0.01"), 2) == Decimal("0.42")`
9. `float` input to every money path raises `MoneyTypeError` (adversarial, not in §9).
10. 100% pass, **0 skipped**, 0 xfail, 0 flaky.
