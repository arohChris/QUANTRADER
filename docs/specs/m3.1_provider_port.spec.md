## Laws (carry-over, binding)

- Historical Depth Law (m3.1 spec): `required_bars = ceil(history_duration /
  timeframe_duration)`; bars declared = `minimum_history + warmup`; depth never
  hard-coded ("take last 50 rows" banned — bible §6a.2b, A65 directive:
  1m→1day-style depth tables banned outright).
- Planner Dependency Law: union over the transitive dependency closure — one
  window per timeframe, widened by the widest requirement.
- PIT-vs-Depth Law: `as_of` = temporal boundary only; `window_end = as_of`.
- A46 WARM responsibility boundary: range args verbatim, never auto-expanded;
  PIT filtering happens **above** WARM — i.e. in this provider, never in warm.py.
- Time law: every datetime tz-aware UTC; naive → typed rejection (no silent UTC).

## Inputs / Outputs / Invariants — resolver

`resolve(*, requirements: tuple[TemporalRequirement, ...], as_of: datetime,
timeframe: str) -> TemporalResolution` (sync `def`, pure):
- In: `requirements` ≥1 (dependency-closure order irrelevant — we take max);
  `as_of` aware-UTC; `timeframe` ∈ `shared.timeframes.INTERVAL_MINUTES` (9
  strings; calendar `1w/1mo/1y` reject).
- Out (frozen `TemporalResolution`, extra=forbid):
  `window_end: datetime = as_of`;
  `window_start: datetime = as_of − needed_bars × timeframe_minutes`;
  `needed_bars: int ≥ 1`.
- Formula per requirement: `bars_r = max(minimum_history + warmup,
  ceil(history_duration_minutes / tf_minutes))` when `history_duration` set,
  else `minimum_history + warmup`; `needed_bars = max(bars_r)` over the tuple.
- Invariants: `window_start < window_end`; span exactly `needed_bars × tf`;
  shifting `as_of` shifts both ends, span constant; no float (int minutes only).

## Inputs / Outputs / Invariants — PIT provider

`PITCandleProvider(store: CandleRangePort)`:
- `CandleRangePort.read_1m(provider, instrument_id, window_start, window_end)
  -> list[Candle]` (async) — structural match to m2.10 `Candles1mStore.read_1m`.
- `async def get_candles(instrument_id, timeframe, window_start, window_end,
  as_of, broker) -> list[Candle]` (§6a.4 signature unchanged):
  1. Validate: all six args present; every datetime aware-UTC (naive →
     `ValueError`); `window_start < window_end` else `ValueError`;
     **`window_end ≤ as_of` else `ValueError`** (PIT violation fails closed —
     never silently clamped).
  2. `store.read_1m(_provider_for(broker), instrument_id, window_start, window_end)`.
     Day-1 `_provider_for`: identity (`"deriv"→"deriv"`, …) — M2 provider names
     coincide with broker names today; the helper is the seam for M2b mapping
     later (WHY comment, single place).
  3. Filter every row: `window_start ≤ interval_start` (defensive re-filter —
     store may over-return) AND `interval_end ≤ window_end` (completion —
     forming-candle leak blocked) AND `interval_end ≤ as_of` (**Day-1
     availability proxy**: closed bar = known at close; see Open Q).
  4. Sort ascending by `interval_start` (chronological law — defensive; store
     already ORDER BY).
  5. Store exceptions propagate untouched (engine flow 6 wraps them as
     `FeatureEngineDataError` — provider never swallows, never returns partial).
- Empty result is **valid** (`[]` → engine quality gate emits `INSUFFICIENT`).
- No SQL built here: values pass as asyncpg parameters (injection-safe WHY).

## Edges (one test each — spec §2.3)

Resolver:
- E1 empty `requirements=()` → `ValueError`.
- E2 naive `as_of` → `ValueError`; unknown timeframe `"7m"`/`"1w"` → `ValueError`.
- E3 invalid `history_duration` (`"0d"`, `"3w"`, `"abc"`) → `ValueError`
  (fullmatch `(\d+)([mhd])`, nonzero — parity with engine's old parser).
- E4 bars-only: `min=20,warmup=5` @`"5m"` → `needed_bars=25`, span 125 min.
- E5 duration-ceil: `(min=1, dur="3d")` @`"5m"` → 864 bars (4320/5 exact);
  @`"15m"` → 288; `(min=1, dur="1d")` @`"24h"` → 1.
- E6 union max: requirements (25@1m), (864 via 3d@5m), (40+0) → 864 — widest
  wins regardless of order in the tuple.
- E7 warmup widens: `min=200,warmup=50` → 250 (m3.1 §8b 200/250 example).
- E8 `as_of` shift keeps span constant; `window_end == as_of` always.
- E9 `min=1,warmup=0` (tick_rate) → `needed_bars=1`, span = 1 tf.
Provider:
- P1 happy: fake store receives exact 6 mapped args (`provider==broker` Day-1),
  returns rows unsorted → provider returns sorted, filtered `[]`→ fine.
- P2 **NO LOOK-AHEAD golden**: rows through 10:10, `as_of=08:00` → every
  returned `interval_end ≤ 08:00`; count matches closed-bar count.
- P3 forming candle (`interval_end > window_end`) excluded.
- P4 `window_end > as_of` → `ValueError` (fail-closed, message says PIT).
- P5 `window_start ≥ window_end` → `ValueError`; any naive datetime →
  `ValueError`.
- P6 store returns row outside `[window_start, window_end]` (misbehaving store)
  → filtered out.
- P7 store raises → exception propagates unchanged (same type reaches caller).
- P8 as_of before all rows → `[]` (not an error).
- P9 timeframe `"1m"` rows requested — provider does NOT re-check interval
  (engine wrong-series guard at flow 6 remains the checker; division of
  responsibility documented).

Adversarial (not in spec's happy list — must fail safe):
- X1 `instrument_id="'; DROP TABLE candles_1m;--"` → passed verbatim as a
  parameter; no crash, no SQL built, store receives it unchanged (assert the
  recorded arg).
- X2 `history_duration="999999999d"` → exact int math (Python bigint), assert
  exact `needed_bars`, no overflow/float.
- X3 store returning 10_000 rows → filter+sort complete, `len` exact (bounded
  adversarial, no truncation).
