## Parameter & context flow (human reminder 2026-10-02 — what strategies "collect and pass down")

Three layers, distinct homes, no leakage between them:

**Layer 1 — Context (collected with the strategy run, passed DOWN to the
underlying analytics engine — never into `evaluate`):**
- `user_id` + `broker` (tenant + capability gate: `is_strategy_eligible(NAME, broker)`;
  per-user vault/private data stays M1.4-scoped), `instrument_id`, `asset_class`,
  `env` (paper/live).
- `timeframe` (TF) — rides `FeatureRequest.timeframe` → selects which candle
  series every slot analytic computes on (S6-style HTF reading later reuses this,
  no contract change).
- PIT info "where to start from": `as_of` T → Temporal Resolver →
  `window_start/window_end` (availability_time ≤ T — §6a law, `pit_provider.py`)
  → the exact candle window handed to analytics. Look-ahead impossible by construction.
- DB/rerun provenance: replay inputs (`reference_snapshot_id`, stored request
  window) re-feed the same `FeatureRequest` so a rerun reproduces identical
  features (M8/M2 lineage) — collected at the runner, resolved before compute.
These fields already exist on `StrategyRunner.run(...)` and `FeatureRequest`
(feature_engine.py:93+) — this slice ADDS NO new plumbing for them; it only pins
that they flow around `evaluate`, not through it.

**Layer 2 — Strategy tunables (the "parameters the strategy will read from
later", admin-managed):** precedence **request overrides (M1.5
`strategy_subscriptions.params` JSONB, admin REPLACE) > `config/strategies/<name>.yaml`
> `PARAM_DEFAULTS`** → (a) `evaluate(features, params)` as `dict[str, float]`,
(b) per-slot `param_overrides` onto the FeatureRequest (e.g. `ema_20@period=10`).
Admins change params; users never (M1.5 ruling).

**DB user-preference briefing (human essence 2026-10-02 — why these rows exist):**
the user runs trades with **their** preferred settings — timeframe + selected
asset(s) + auto-trade click. The system honors them: at every fire instant
(`activation_at + n × tf` via `next_run_at`; user changes tf → cadence
recomputed, anchor kept), on the user's selected asset and TF, the strategy
checks whether the market **currently** satisfies its requirements (gates +
trigger via `evaluate`) — non-zero strength continues to M5 risk → order;
`0.0` = no order this fire. Row read fresh **before every evaluation — no read
→ no run** (`StoreError` fail-closed).

The runner reads `TradingPrefsStore`
(`shared/core/trading_prefs_store.py` — fail-closed: any `StoreError` → the
strategy runs NOTHING) per `(user_id, broker_id)` and feeds strategies from:
- `trading_preferences.timeframe` → the TF every slot analytic computes on
  (via `FeatureRequest.timeframe`);
- `trading_preferences.activation_at` + `auto_trade` → when/if the run starts
  (schedule anchor + user master switch, default `False`);
- `strategy_subscriptions.user_disabled` → per-strategy user off-switch;
- `strategy_subscriptions.params` → the top-precedence params dict handed to
  `evaluate(features, params)` (REPLACE wholesale — the store never merges);
- `strategy_subscriptions.instruments` → allowed instruments (empty set =
  trade nothing);
- `strategy_admin.admin_approved` → global gate (missing row = default TRUE).
Writes are registry-gated (`known_strategies` — unknown `strategy_id` dies
typed before SQL); consumption happens at the runner (Step C). `evaluate` still
receives features + float params only.
- Run-rule gate itself is NOT implemented here: pure conjunction in
  `shared/core/trading_run_rule.py` (`admin_approved AND auto_trade AND NOT
  user_disabled AND instruments != []`), wired in M1.5 Step C — m4.7 only
  consumes the briefing fields above.
- Schedule = `shared/core/analysis_schedule.py::next_run_at` (activation
  anchor, repeat each tf interval; tf change recomputes cadence from next fire).
- Ordering: the 5 new strategies become admin-approvable/subscribable only
  after their registry names land (Slice 5b).

**Layer 3 — Analytic defaults:** `REQUIREMENTS.defaults` (lowest precedence).

**Invariants:** `evaluate` stays the m4.2 pure float contract (features + float
params only — no user_id/broker/TF/PIT args: those would leak I/O context into
pure compute and break determinism/replay); context resolution happens BEFORE
`evaluate` (engine/PIT/provider); no strategy or analytic file may open a DB or
lake (`check_pit_guard.py` + Isolation Law enforce this slice too).
**Single-context atomicity (human 2026-10-02: "the most important thing —
every analysis under a strategy shares the same info in timing and TF"):**
one `FeatureRequest` → ONE resolved timeframe + ONE window + ONE candle list,
and every slot analytic of the strategy computes on that identical data.
Verified in the existing engine (`feature_engine.py:get_features`): resolve
once (:201-204), single `get_candles` (:208-213), `compute(candles, ...)` per
slot on the SAME list (:247), one `resolved_tf` stamped on the result (:265),
`as_of` inside the cache key (:325). Never per-slot windows or TFs — mixed
context would make gate/trigger legs incoherent. Locked by
`test_m4.7_playbook_tier1_spec.py::test_strategy_slots_share_one_request_context`.

## Prerequisite analytics (Step 1 definitions — all: `compute(candles, params) -> float`,
Isolation Law: no provider/clock/as_of; non-finite input → `math.nan` honest refusal;
`params=None` / empty candles → `ValueError`; D4 one file each)

1. **`ema_8` / `ema_21` / `ema_55`** — identical algorithm + first-value seed to
   `ema_20.py` (m3.1 REV4 pin), defaults `{"period": p}` pinned, `NAME` = stem.
   `minimum_history = p`, `warmup = round(0.25*p)` (m3.1 exemplar ratio).
   WHY 3 files: m4.2 rule "all slot analytics within one file must be DISTINCT
   names" — S1 needs three EMAs simultaneously, so `ema_20@override` ×3 is illegal.
   Hand: flat closes `[10]*8` @p=8 → `10.0` exact; period non-integral/`<1` → ValueError.
2. **`last_close`** — last bar's close. `minimum_history=1, warmup=0`.
   Hand: close 105.5 → `105.5`.
3. **`bar_low`** — last bar's low. `minimum_history=1, warmup=0`.
   Hand: low 99.25 → `99.25`.
4. **`close_position`** — `(close - low) / (high - low)` of the last bar, 0..1
   (1 = close at high). Canonical flat-range branch: `high == low` → `0.5`
   (no divide-by-zero; same canonical-branch style as donchian_20).
   Hand: `h=10, l=0, c=7` → `0.7`; `h==l` → `0.5`.
5. **`close_change`** — `close_t - close_{t-1}` (signed). `minimum_history=2`;
   1 candle → `nan`. Hand: closes `…, 101, 103` → `2.0`.
6. **`rejection_bar`** — candle-shape classifier → `+1.0` bullish rejection,
   `-1.0` bearish, `0.0` none. Definitions (book says "bullish rejection candle"
   without spelling it out — pinned here): body = `|close-open|`; bullish iff
   `body > 0 AND (min(open,close) - low) >= 2*body AND close >= low + 0.5*(high-low)`;
   bearish iff `body > 0 AND (high - max(open,close)) >= 2*body AND
   close <= high - 0.5*(high-low)`; **bullish checked first** (both-hold tie →
   `+1.0`, documented). Doji (`body == 0`) → `0.0`.
   Hand: bullish `o=10,c=12,l=6,h=12.5` (lower wick 4 = 2×body, c in upper half) → `+1.0`;
   bearish `o=12,c=10,h=16,l=8` (upper wick 4 = 2×body) → `-1.0`; doji → `0.0`.
7. **`sweep_reversal`** — D1 event: wick beyond the prior `window`-bar extreme
   followed by a close back inside, with a confirming close at bar `i`.
   Output `+1.0` (low sweep + bullish confirming close → long), `-1.0` (high sweep +
   bearish confirming close → short), `0.0` none. Params: `window` 20.0
   (integral ≥ 5), `within` 2.0 (integral ≥ 1).
   Algorithm (pinned): let `i = len-1`. Min-history guard: fewer than `window`
   prior bars (`i < window`) → `nan`. Candidates `j ∈ [max(0, i-within), i]`;
   for each `j` the trailing window `candles[j-window : j]` MUST be full
   (`j >= window`, fail-closed — a short window cannot sweep; no short-window
   phantoms). High-sweep at `j`: `high_j > max(candles[j-window:j].high)` AND
   `close_j <= that max` (wick beyond prior extreme, close back inside).
   Low-sweep mirrored with `min(...lows)`.
   Direction SELECTED BY the confirming close of bar `i`:
   `close_i > open_i` → require low-sweep somewhere in the candidate window → `+1.0`;
   `close_i < open_i` → require high-sweep → `-1.0`; equal closes → `0.0`.
   Hand: bars 0..19 highs max 100 (closes inside), bar 20 `o=99.5,h=101,l=98,c=99`
   (sweep up + back inside), bar 21 `o=99,c=98` (bearish confirm, within 1 ≤ 2)
   → `-1.0`. Same setup with bar 21 `o=98,c=99.5,h=100.5,l=98` (bullish confirm —
   `l=98` equals the window min, so NO low sweep exists anywhere even though
   `h=100.5` makes a high sweep) → `0.0` (side must match).
8. **`supertrend_flip`** — S5 trigger: fresh direction flip of the classic
   Supertrend. Params: `mult` 3.0 (finite > 0), `period` 10.0 (integral ≥ 1).
   `minimum_history = 11` (default period+1), `warmup = 0`.
   Algorithm (pinned, hand-verifiable):
   - `TR_0 = h-l`; `TR_t = max(h-l, |h-close_{t-1}|, |l-close_{t-1}|)` (atr_14 TV convention).
   - ATR series: `atr_t = mean(TR_0..TR_t)` for `t < period-1`;
     `atr_{period-1} = mean(TR_0..TR_{period-1})`;
     `atr_t = (atr_{t-1}*(period-1) + TR_t)/period` after.
   - `mid = (h+l)/2`; `basicU = mid + mult*atr`; `basicL = mid - mult*atr`.
   - `U_0 = basicU_0`, `L_0 = basicL_0`;
     `t≥1`: `U_t = basicU_t if (basicU_t < U_{t-1} or close_t > U_{t-1}) else U_{t-1}`;
     `L_t = basicL_t if (basicL_t > L_{t-1} or close_t < L_{t-1}) else L_{t-1}`.
   - `dir_0 = +1 if close_0 >= mid_0 else -1`;
     `t≥1`: `dir_t = +1 if close_t > U_{t-1}` elif `-1 if close_t < L_{t-1}` else `dir_{t-1}`.
    - Output: `+1.0` fresh up-flip, `-1.0` fresh down-flip, `0.0` otherwise;
      **fresh = flip at the LAST bar** (`dir` changed at `i`; a flip earlier in
      the series that merely carries at `i` → `0.0`); 1-bar input → `0.0`
      (no previous bar).
   Hands (period=2, mult=1; fixtures use `open=close` — Supertrend ignores open):
   - Up-flip: bars `(h,l,c)` = `(10,8,8)`, `(11,9,10)`, `(12,10,11.5)`
     → `U=[11,11,13.25]`, `L=[7,7.5,8.75]`, `dir=[-1,-1,+1]` → `+1.0`.
    - Down-flip: `(10,8,9)`, `(9,7,8.5)`, `(8,6,6.5)`
      → `U=[11,10,9.25]`, `L=[7,7,4.75]`, `dir=[+1,+1,-1]` → `−1.0`.
   - No flip (first two bars of the up-flip setup): `dir=[-1,-1]` → `0.0`.
   - Single bar → `0.0`; flat 12-bar series with defaults → `0.0`.

## Strategies (m4.2 contract — gates+trigger → house ramp; execution fields OUT)

House ramp (m4.2 §): `sign * (0.5 + 0.5*min(1.0, progress))`, `progress ∈ [0,1]`,
so a just-triggered signal is `±0.5`, never ambiguous with `0.0` = no signal.
Input contract (m4.2): every slot present + finite else `ValueError`; `params=None`
→ `ValueError`; `params={}` → defaults applied inside `evaluate` via `.get`;
unknown param keys ignored; out-of-bounds params → `ValueError`; result always in
`[-1, +1]`; deterministic; no state/I/O/clock.

- Trigger — **ALL three must hold** (pinned from card pseudo
  `if not (touched and reversal and rsi(...)>40): return None`):
  `touched = |close - ema| <= touch_atr*atr`;
  `reversal = cpos >= cpos_min AND low > swlow` (book pseudo applies the bull
  shape to BOTH directions — followed literally; mirrored short shape is a
  recorded `TODO(correctness)` question, not a silent change);
  `rsi > rsi_min` (pseudo literal for both directions).
- Sign: `state` (+1 long / −1 short). Progress: pullback quality
  `1 - min(1, dist/(touch_atr*atr))`, `dist==0` → `1.0` (no 0/0; if `dist>0` then
  `touched` already implies `atr>0`).
- Hands: gate-max + `close==ema` → `+1.0`; `dist = touch_atr*atr` → `+0.5`;
  `dist=0.125*atr` (atr=1) → `+0.75`; short-state mirror → `−1.0`;
  `er == er_min` (0.3) → `0.0` (strict); `atr=0` + `close==ema` → `+1.0` exact touch;
  trigger legs are AND — touch miss (`dist=0.5*atr`) → `0.0`, `cpos=0.3` → `0.0`,
