# Spec: M1.5 Trading Preferences + Strategy Subscriptions (per-user strategy briefing store)

Purpose: Store, per user+broker, the info a strategy needs before it may analyze
anything — **timeframe, activation time, auto-trade switch** — plus per-strategy
subscription state, and derive the analysis schedule: **repeat every tf interval until
the user changes tf (which also updates the scheduler)**.

Behavior law (human, 2026-09-30): **admin approves the strategy globally — available
to all users by default; a user can then turn a strategy off. When a user clicks
auto-trade, enabled strategies run in the background on the asset(s) the user selected
for that trade; the user may add another trade, but it must pass the risk threshold
before it runs.**

Row lifecycle (human, 2026-09-30): **once a user signs in to the platform, the
available info is already written to the preferences; when the user connects a broker
account, that info is added to the preferences as well; fields the system can update
by itself are auto-updated.**

## Row lifecycle (human: sign-in writes; broker connect adds; system auto-updates)

Helpers on the repository (wired to auth/broker events in Step B, defined+tested here):

1. **`ensure_at_sign_in(user_id)`** — first sign-in: user's available info lands in
   preferences. If a broker is already connected, materialize that (user, broker) row
   now; otherwise the settings are held and materialized at broker connect (PK needs
   a broker). Defaults: tf '1m', activation_at = now, auto_trade FALSE.
2. **`ensure_at_broker_connect(user_id, broker_id)`** — broker connect: materialize the
   (user, broker) row — broker-scoped info added; **existing user-set fields (tf,
   activation, auto_trade) preserved — added, never clobbered.**
3. **Auto-updated fields** (no user action): `updated_at` on every write, default
   materialization at lifecycle events, schedule recomputation after tf change.
4. **Idempotent:** running either helper twice = no change (UPSERT, no duplicates,
   no clobber).

## Run rule (fail-closed — human semantics folded into lock a + b)

```
run  <=>  admin_approved(strategy)              # GLOBAL platform flag (default TRUE)
      AND auto_trade(user, broker)              # user master switch (default FALSE)
      AND NOT user_disabled(user, broker, strategy)   # per-user opt-out
      AND instruments != []                     # at least one selected asset
```

- Runner reads the subscription row `WHERE user_id+broker_id+strategy_id` **before
  every evaluation**. No read -> no run.
- Store error / timeout / ambiguous state -> typed `StoreError` -> **no run**
  (`UNKNOWN -> REJECT` §3.3).
- **Precedence CHANGE vs `modules/m4_alpha/strategy/lifecycle.py:29`:** the global
  admin flag (and platform kill) can never be resurrected by a user row; a user's
  opt-out can never be overridden by platform defaults. Wiring `Lifecycle` to this
  rule = Step C; the rule itself is fixed here.
- Every concrete trade instance (first asset or added asset) additionally passes the
  **M5 structural pre-trade risk threshold** before running (§3.3) — Steps B/C.

## Schedule rule (human: repeat at tf interval; tf change updates the scheduler)

Pure helper `next_run_at(activation_at, timeframe, now) -> datetime`
(sync `def`, no I/O; interval from `INTERVAL_MINUTES`; lives `shared/core/analysis_schedule.py`):

- Run instants: `activation_at + n * tf_minutes` for `n = 0,1,2,...`
- `next_run_at` = smallest such instant `>= now`.
- **User changes tf -> UPSERT new interval, anchor UNCHANGED, next fire recomputed.**
- `now < activation_at` -> next fire is `activation_at` itself (n=0): scheduled wait.

## Edges (one test each, named after the edge)

Run rule:
- admin_approved FALSE (global) -> run denied for EVERY user (cross-user effect)
- auto_trade FALSE -> run denied even if everything else allows (default state!)
- auto_trade TRUE + user_disabled TRUE -> run denied (user turned strategy off)
- auto_trade TRUE + instruments == [] -> run denied (trade nothing)
- all four inputs allow -> run allowed
- no subscription row -> defaults: flags allow, instruments [] -> no run until asset
  selected
- no preferences row -> auto_trade defaults FALSE -> no run until user clicks
- unknown strategy_id in admin table on write -> typed error (registry)

Row lifecycle:
- ensure_at_sign_in twice -> idempotent, single row, no clobber
- ensure_at_broker_connect after user set tf '4h' -> tf '4h' preserved, broker info added
- ensure_at_broker_connect for second broker -> second (user, broker) row from template,
  first broker's row untouched

Schedule:
- future activation_at -> next_run_at returns activation itself (scheduled wait)
- past activation_at -> smallest anchor+n*tf >= now (no missed-forever)
- tf change (1m -> 1h) -> same anchor, next_run recomputed with new interval
- run instants land exactly on anchor + n*tf (n=0,1,2 asserted)

Validation:
- timeframe '1w' (calendar bucket) -> ValidationError (registry law)
- timeframe '1m; DROP' / unknown key -> ValidationError, CHECK + pydantic
- naive activation_at (no tz) -> ValidationError (tz-aware UTC, §3.8)
- activation_at year < 2000 -> ValidationError (sane bound §3.13)
- params = JSON array/string -> ValidationError (must be object)
- unknown strategy_id on subscription write -> typed error (registry)
- UPDATE tf twice -> single row, last write wins, updated_at advances (UPSERT atomic)
- cross-tenant: read for user A never returns user B's row (same strategy/broker)
- DB connection error on read -> StoreError -> no run
- repository not wired -> StoreError -> no run (defaults apply only to absent ROWS,
  never to absent READS)

## Adversarial (beyond the edge list)

- SQL/registry injection attempt: `strategy_id = "x'; DROP TABLE--"`,
  `user_id = "' OR '1'='1"` -> parameterized queries; unknown strategy rejected with

## REV5 amendments (2026-09-30 — Top-10 test-review additions + human rulings)

Human verdict on the original 48-test suite: "approve as a strong RED-phase
specification, not yet a complete production acceptance suite" — the 10
additions below gate `complete`. Condensed findings:
`M1.5_Test_Review_Findings.docx` (repo root). Build approval: "others lgtm"
(2026-09-30).

1. **Integration layer = verify script, not pytest.** The suite stays hermetic
   (0 skips allowed; no server needed). CI has NO Postgres service. Real-Postgres
   coverage runs through `scripts/verify_m1.5_trading_prefs.py` (EXIT 0 required,
   human eyeballs) — repo convention (m2.7/m2.9/m2.10 all live-verify via
   scripts). Flagged: a future CI slice may add a PG service; until then this is
   the documented split.
2. **Write failures (every operation).** Each of `set_timeframe`,
   `upsert_subscription`, `set_admin`, `ensure_at_sign_in`,
   `ensure_at_broker_connect` under an injected execution failure -> raises
   `StoreError`; no partial state claimed, rows unchanged.
3. **Cross-broker SUBSCRIPTION isolation.** `(u1, deriv, S)` never returned for
   `(u1, mt5, S)` — the full-PK law asserted explicitly for the subscription
   table, not only by construction.
4. **Concurrency semantics (documented law).** LAST COMMITTED WRITE WINS; the
   row UPSERT is the serialization point (§3.6). Within one store instance
   concurrent async writers resolve by execution order; cross-process ordering
   is Postgres commit order. Tests: interleaved concurrent writes leave exactly
   ONE stable row whose value is one of the writers — never a duplicate, never a
   torn row. Step C runner is single-process (assumed here).
5. **Params = REPLACE, and params are ADMIN-managed (human ruling verbatim
   2026-09-30: "a user can not set this — if it needs to change, admins will do
   that").** The store replaces the `params` object wholesale on every write
   (never merges — merging hides data loss). Users never write `params`: Step B
   exposes them to users READ-ONLY; changes arrive only via admin-authorized
   paths (HTTP authz lands in Step B). Users own: timeframe, activation_at,
   auto_trade, user_disabled, instruments. Supersedes follow-up item 3.
6. **Schedule edge additions.** `activation == now` -> fires at activation;
   seconds-precision anchor (06:00:37 + 1h, now 07:00:15 -> 07:00:37); unknown
   timeframe -> ValueError (typed, never a silent default interval); naive `now`
   -> ValueError (§3.8).
7. **Lifecycle chain test.** sign-in (no broker, no write) -> broker connect ->
   user change -> "sign-out" (no store call; state is DB-persisted by law) ->
   sign-in -> broker connect -> configuration preserved end-to-end, still one
   row, defaults never clobber user changes.
8. **Admin authorization boundary (store level).** ONLY `set_admin` and
   `admin_approved` may execute SQL against `strategy_admin`; every user-facing
   method is asserted to never emit SQL naming that table. HTTP/service-level
   admin authz itself is a Step B deliverable (documented, not testable here).
9. **updated_at strictly increasing, caller cannot forge it.** The store stamps
   its own clock via a monotonic clamp (`updated_at = max(now, last + 1µs)` per
   store instance) so consecutive writes are strictly increasing regardless of
   OS clock resolution; caller-supplied `updated_at` on incoming contracts is
   IGNORED (system-managed). Cross-process strictness = commit order (see #4).
10. **Injection breadth.** The bound-parameter law (payload travels as a
    parameter, never in SQL text, all three tables intact) asserted for
    broker_id, instrument ids, and params keys/values. Validation and
    parameterization stay DISTINCT properties: unknown strategy_id fails as
    `UnknownStrategyStoreError` (registry gate), NOT as an injection test.
