# Spec: M4.3 Signal Validation — the bouncer (bible P24 gate: "Drop stale")
# Amended 2026-09-26 per human architecture directive (A65): (a) explicit SCOPE
# boundary — M4.3 never inspects candles/analytics history; (b) check order —
# timestamp-validity is its own step BEFORE freshness (test-neutral: no existing
# test outcome changes); (c) identity + first-match-wins explicitly locked.

Purpose: Gate every `Signal` BEFORE it can reach M5 Risk — reject shadow, expired,
latency-exceeded, duplicate, and untradable signals with a typed rejection; only
clean signals are forwarded. Fail-closed: any doubt → reject (§3.3).
SCOPE BOUNDARY (human, A65): M4.3 validates the SIGNAL CONTRACT only. It NEVER
inspects candles, bar counts, warmup, or how the signal was produced (live tick /
replay / 20 bars / 10,000 bars) — required historical depth is decided UPSTREAM
by the M3.1 requirement planner + quality gate (human architecture lock-in
2026-09-26; provider contract upgrade queued separately, see BUILD_STATUS).

Inputs:
- `signal: shared.contracts.signal.Signal` (frozen contract, M1.1)
- `now: datetime` — caller's UTC-aware clock (deterministic; no hidden clock reads)
- tradable lookup = `modules.reference.reference.exists(instrument_id, broker)` (M2b.1)

Outputs (in-module, `modules/m4_alpha/signal/`):
- pass → the SAME `Signal` (identity preserved, never mutated) or
- frozen `SignalRejection(signal_id, strategy_id, reason, detail, rejected_at=now)`
- `SignalRejectReason` locked enum (6): `shadow`, `stale`, `latency_exceeded`,
  `unknown_symbol`, `duplicate`, `invalid_timestamp`
- `validate_batch(signals, *, now) -> BatchResult(validated: tuple[Signal, ...], rejected: tuple[SignalRejection, ...])`
  — input order preserved; `()` in → `()` out

API (sync `def` — pure + in-memory only, no I/O → no `await` per §4.2):
- `SignalValidator(*, dedup_window_seconds: float = 60.0, latency_budget_seconds: float = 60.0)`
  - either `< 0` → `ValueError` at construction (§3.13 config sanity, fail at startup)
- `validate(signal, *, now) -> Signal | SignalRejection`

**Check order PINNED — first match wins (human-locked sequence A65); only a
fully-passing signal is recorded in the dedup window:**
0. `not isinstance(signal, Signal)` (None/dict/str) → `TypeError` — programmer
   error fails loud, never a silent pass or a fabricated rejection
1. `signal.shadow` → `shadow` (even if also stale — tag beats defect)
2. **timestamp validity:** naive `valid_until` OR naive `signal.timestamp` →
   `invalid_timestamp` (no `TypeError` crash on comparison); `signal.timestamp >
   now` → `invalid_timestamp` (future-stamped signal never validates)
3. freshness: `now > valid_until` → `stale` (equality `now == valid_until` PASSES
   — stale is strictly greater)
4. latency: `now − signal.timestamp > latency_budget_seconds` → `latency_exceeded`
   (equality passes)
5. `reference.exists(signal.symbol, signal.broker)` False → `unknown_symbol`
   (unknown id, unknown broker, or broker not listed for the instrument)
6. dedup key = `(strategy_id, symbol, direction, user_id or "")`; key has a
   recorded entry with `0 <= now − t <= dedup_window_seconds` → `duplicate`
   (the record is NOT refreshed by a rejected duplicate); else record `now` → PASS

**LAW: `signal.symbol` = canonical INSTRUMENT_ID** (`FX.EURUSD`, `CRYPTO.BTCUSD`) —
same as M2.2 `to_canonical` output and the ACTION-35 `symbol=instrument_id` pin.
Display symbols (`BTCUSD`, `EURUSD`) are not tradable keys and reject.

Edges (one test each):
- E1 fresh, tradable, unique, non-shadow signal → returned as-is (same `signal_id`)
- E2 shadow + stale at once → reason `shadow` (order pin: tag beats defect)
- E3 `now > valid_until` → `stale`; E3b `now == valid_until` → passes (boundary)
- E4 naive `valid_until` → `invalid_timestamp` (no `TypeError` crash)
- E5 age 60.000001s vs default budget 60 → `latency_exceeded`; E5b age exactly
  60.0s → passes; E5c `latency_budget_seconds=0.1` honored (microstructure-ready)
- E6 `signal.timestamp > now` → `invalid_timestamp`; E7 naive `signal.timestamp`
  → `invalid_timestamp`
- E8 unknown symbol → `unknown_symbol`; E8b known instrument + wrong broker →
  `unknown_symbol`; E8c `CRYPTO.BTCUSD`+`deriv` → passes (real master)
- E10 duplicate within window → `duplicate` (HC-1); E10b same key after window →
  passes (HC-2)
- E11 different direction, different strategy, or different `user_id` (same
  symbol/broker) → each passes — dedup key includes all four parts
- E12 rejected duplicate does NOT refresh the record (HC-3)
- E13 `validate_batch`: mixed list splits correctly, order preserved; empty in →
  empty out
- E14 rejected (stale) signal is never recorded — a later fresh signal with the
  same key passes (dedup records only full passes)
- E15 naive `now` → `ValueError` (caller bug, typed)
Adversarial: ADV1 `validate(None)` / `dict()` → `TypeError` naming the type; ADV2
`symbol="'; DROP TABLE instruments"` → `unknown_symbol`, no crash, no DB touched;
ADV3 `latency_budget_seconds=-1` → `ValueError` at construction.

Correct: window/latency arithmetic = datetime subtraction → `total_seconds()`
float compare; boundaries exact as pinned above. No money math — explicit timing
hand-calcs (proof anchors):
- HC-1 window 60: record T=09:00:00; identical key at 09:01:00.000 → age 60.0 ≤ 60 → duplicate
- HC-2 identical key at 09:01:00.001 → age 60.001 > 60 → record pruned → passes
  (test raises `latency_budget_seconds` to isolate dedup: with the default 60s
  budget the latency step fires first at age >60 — pre-impl arithmetic catch,
  A65 amendment, no default changes)
- HC-3 record 09:00:00; dup rejected 09:00:30 (record still 09:00:00); resend
  09:01:01 → age 61 > 60 → passes (rejections never refresh the window;
  latency budget likewise raised in the isolating test)
- HC-4 budget 60: age exactly 60.0 → passes; age 60.000001 → latency_exceeded
