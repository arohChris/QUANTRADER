# Spec: M10.4.10 — Trade-ticket timeframe dropdown + full-registry timeframe vocabulary

Status: draft for human review (Step 1) — 2026-09-30
Frontend module: M10.4 (`frontend/` — own specs/tests/`FRONTEND_BUILD_STATUS.md`)
Backend changes: **NONE.** Backend law consumed read-only:
`financial_analyst_app/shared/timeframes.py` (`INTERVAL_MINUTES`, 9 keys).
Queue origin: `docs/specs/m3.2_book_feature_library.spec.md` §10 Q5 (human design
decision 2026-09-30). Human directive 2026-09-30: **"include all timeframes"** —
the UI offers the complete registry, never a subset.

## Purpose

Every timeframe choice the UI offers is exactly the backend registry (all 9
values), and the manual trade ticket gains the required timeframe field — so no
user selection can ever be a value the backend hard-rejects (`FeatureRequest` /
Temporal Resolver reject anything outside the registry).

## Inputs

- **Registry (source of truth, read-only):** `shared/timeframes.py`
  `INTERVAL_MINUTES` keys = `{1m, 5m, 15m, 30m, 40m, 1h, 2h, 4h, 24h}` (9,
  fixed-duration only; calendar buckets `1w/1mo/1y` deliberately absent).
- **Frontend parity copy:** `app/experiment_market.ts` `MOCK_TIMEFRAMES`
  (name kept deliberately — it still drives the mock chart window; renaming
  would churn tests/docs for zero behaviour gain; WHY comment records the lock).
- **User selection:** ticket timeframe select (explicit; no default).

## Outputs

- `TradingTicket.tsx`: required select `#trade-timeframe`, options = all 9
  (mapped from the shared constant), placeholder `Select timeframe`
  (`value=""`, no `defaultValue`), ticket state holds `timeframe: string`.
- `MarketPanel.tsx` chart select: same constant → 9 options (was 6, of which 3
  were illegal `1H/4H/1D`). No component change needed — it already maps the
  constant.
- `TIMEFRAME_WINDOW`: presentation window size for every one of the 9 keys
  (new keys `30m/40m/2h/24h`, each ≤ `MAX_POINTS` 64, presentation-only).

## Invariants

- **I1** `set(MOCK_TIMEFRAMES) == set(INTERVAL_MINUTES)` exactly — 9 both
  directions, no dups. Parity test is law (frontend mirror of backend
  `test_tf_registry_parity_with_m2_candles`).
- **I2** No silent default: the ticket select starts `""` with a placeholder
  option; nothing preselects a timeframe.
- **I3** Vocabulary: zero `"1H"`/`"4H"`/`"1D"` (quote-wrapped) anywhere in
  `frontend/app/**`.
- **I4** No calendar buckets (`1w/1mo/1y`) or malformed keys in the constant.
- **I5** One source: ticket and chart map the SAME constant — a second literal
  timeframe list in any component fails I6-style single-source check.
- **I6** Mock law preserved: no `fetch`/`websocket`/`x-role` in the ticket;
  Preview/Confirm stay disabled (write path returns with M6, per
  `FRONTEND_BUILD_STATUS.md` `/trade` + `/confirm` decision).

## Amendment A — asset chooser + multi-trade (human directive, 2026-09-30, same session)

**A1 — Asset is chosen, not typed.** The ticket's Instrument field becomes a
single `<select>` over `MOCK_INSTRUMENTS` (the 12-entry catalogue; values are
the canonical ids `FX./CRYPTO./COMMODITY.`, labels the display names).
Default = first entry `FX.EURUSD`, preserving the previous hardcoded value —
no behaviour change, and unlike timeframe this default is intentional (the
catalogue always has a valid first member; timeframe needed an explicit pick
because any wrong string is a backend reject). No free text: a typed
instrument could be any string; the catalogue is what the chart selector
already offers.

**A2 — No one-trade-at-a-time limit.** The ticket is reusable — each future
submit is one trade, and neither the UI nor the frozen contracts limit a user
to one concurrent trade (`Order`/`PortfolioState` are collections; the Orders
surface already renders a chain). Verified by absence: nothing in the ticket
disables it after a selection. **No code change and no test** — recorded
because the requirement was stated explicitly; any future single-trade lock
must be a new spec, never a silent addition.
